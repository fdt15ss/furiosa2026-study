## 1. NPU 개요

### 1-1. 학습 vs 추론

- **학습(Training)**: 순전파 → 손실 계산 → **미분(역전파)** → 가중치 갱신
  - 수식으로 보면 `y = Wx + b`, 갱신은 `W = W - learning_rate × (∂loss/∂W)`
- **추론(Inference)**: 이미 학습된 가중치로 `y = Wx + b` 계산만 수행 (`model.predict` 에 해당)
- 강사 설명: **NPU는 GPU에서 "학습(가중치 갱신) 부분을 뺀" 추론 특화 칩**이라고 보면 이해가 쉬움
  - 예) ChatGPT에 질문하고 엔터를 쳤을 때 나오는 답 = 추론. 그 자리에서 학습을 돌리면 결과가 두 달 뒤에 나옴
- 서비스 서버에는 학습용 연산 장치가 필요 없기 때문에, **서비스(추론) 쪽에서는 NPU가 유리**
  - 가격이 낮고, 전력 소모가 적고(강사 언급: GPU의 절반 정도), 추론 속도는 비슷하거나 약간 빠름(강사 언급: 약 1.1배)
- 다만 **학습은 여전히 GPU**를 사용 (GPU는 물량 부족이 문제)

### 1-2. GPU vs NPU 비유 (강사 설명)

- CPU vs GPU: 강호동 8명 vs 유치원생 4,000명 — 무거운 물건 하나는 강호동이, **가벼운 일을 대량으로 병렬 처리**하는 건 유치원생(GPU)이 빠름
- NPU는 이 병렬 연산을 **AI 추론에 맞게 더 특화**한 칩

### 1-3. 퓨리오사 vs 리벨리온

- 강사 후기: 성능은 퓨리오사가 더 좋다는 평가가 있지만, **서비스/기술지원 응답 속도** 때문에 리벨리온 쪽으로 넘어가는 경우가 많음
- 원인: 지원을 **수작업**으로 하고 있어 주문이 몰리면 병목이 생김 → 병목만 해결되면 개선될 것으로 전망
- 현재 주문이 약 2달 치 밀려 있고, 자체 양산은 아직 초기 단계

## 2. 용어 정리

| 용어 | 의미 | 비고 |
| --- | --- | --- |
| **TPS** | Tokens Per Second, 초당 처리 토큰 수 | 버스 타면서 찍는 "토큰"이 아니라 LLM 토큰. 추론 속도 지표 |
| **KV 캐시** | Key / Value 캐시 | 트랜스포머 어텐션에서 이전 토큰의 Key·Value를 저장해 두고 재사용해 추론 속도를 높임 |
| **TCP** | Tensor Contraction Processor (퓨리오사 칩 구조 이름) | 강사: 이름일 뿐 큰 의미는 없음. TCP/IP와 다름 |
| **컴파일** | 만들어 둔 모델을 NPU에서 **오프라인 실행 가능한 형태로 변환** | 학습이 아님. 한 번 돌리면 **최소 2시간 이상** 걸림 |
| **양자화** | 가중치를 낮은 정밀도로 줄여 경량화 | 이번 환경에서는 안 될 것 같다고 언급 |
| **EFX/ENF 류 바이너리** | 퓨리오사용 컴파일 산출물 파일 | 녹취가 불명확. "익스텐디드 바이너리" 약자로 설명됨 — 확인 필요 |

> **포인트**: KV 캐시는 **트랜스포머 구조에서 가장 중요한 개념 중 하나**이며, 발표 때 계속 질문이 나올 것이라고 강조함 (Key/Value가 무엇인지 설명할 수 있어야 함).
> 이전에 배운 트랜스포머 어텐션(Q, K, V)과 연결해서 복습할 것.

### 컴파일 실습 예정

- 대상 모델: **Qwen3, Llama 3.1** 등 — Hugging Face에 올라온 모델을 내려받아 컴파일해 보기
- 컴파일은 오래 걸리므로 엔터 치고 나서 다른 작업을 하며 기다려야 함
- 얼마나 걸리는지, 어떤 모델이 잘 돌아가는지 직접 테스트할 예정

## 3. 서버/리소스 구성

- 제품: **퓨리오사 RNGD(레니게이드)** — 카드 1장당 **48GB** 메모리
- 서버 1대에 RNGD **4장** 장착 (8장까지 가능하지만 발열 문제로 4장)
- 서버를 **Kubernetes 파드(Pod) 4개**로 나눠서 사용 → 파드 안에서는 root 권한을 주지만, **파드 단위로 격리**되어 있어 문제가 생겨도 해당 파드 안에서만 영향
- 오프라인 모델을 제대로 돌리려면 **카드 2장 이상 병렬 연결**이 필요한 경우가 많음
- 프로젝트 기간: 5명 팀당 카드 2장, 11월 26일경 파드 2개를 엮어서 사용할 예정

### 내가 받은 기본 리소스 (접속 가이드 기준)

| 항목 | 값 |
| --- | --- |
| CPU | 16 코어 (일부 12 코어) |
| 메모리 | 80GB |
| 스토리지 | 128GB |

### 서버 물리 사양 확인 (`lscpu`, `free`)

- CPU: 32코어/64스레드 × 2장 = **128 스레드**
- 메모리: 서버 전체 약 **1TB** (우리에게는 그중 80GB가 파드로 할당)
- `furiosa-smi status` 에 코어가 8개 보이는데, 이는 **CPU 코어가 아니라 NPU 안의 병렬 처리 블록(PE 묶음)** 이라고 이해하면 됨 (CUDA 코어 수만 개와 직접 비교하기 어려움)

### 주의사항

- 작업은 **지정된 홈/폴더(루트 하위 특정 디렉토리)에서만** 할 것 — 파드가 재시작되면 다른 경로 파일은 사라질 수 있음
- 남의 키·포트 번호를 건드리지 말 것 (어차피 키와 매칭되어 접속되지 않음)

## 4. 포트 개념

- **22번 포트**: SSH 접속용
- **8000번 포트**: 웹 서비스(웹 앱/API 테스트)용
- 그 외 포트는 현재 막혀 있음 (추가가 필요하면 별도 요청 — 수작업으로 열어줌)
- 사람마다 포트 번호가 다름. 예) 1번 → `37010`(SSH) / `37011`(8000), 4번 → `37040`
- 포트 = 건물에서 어느 문으로 들어갈지 정하는 번호라고 이해

## 5. WSL 다중 배포판 만들기 (PowerShell)

한 PC에서 **용도별로 WSL 배포판을 여러 개** 만들어 쓰는 구조 (Hermes, 퓨리오사, OpenClaw, PyTorch, TensorFlow 등을 각각 분리).

### 핵심 명령어 (PowerShell)

```powershell
wsl -l -v                      # 설치된 배포판 목록과 버전 확인
wsl --install <배포판>          # Ubuntu 설치 (예: Ubuntu-22.04)  (보충)
wsl -d <배포판이름>             # 특정 배포판으로 접속
wsl --list --online            # 설치 가능한 배포판 확인          (보충)
```

- 강사 가이드: **그냥 `wsl` 로 들어가지 말고** 먼저 `PowerShell` 을 켠 다음 `wsl -l -v` 로 확인하고 `wsl -d 이름` 으로 접속
  - 그냥 `wsl` 은 별표(\*) 가 붙은 **기본(메인) 배포판**으로 바로 들어가 버림
- 이름 규칙: 팀 전체가 통일 — 배포판 이름 `furiosa01`, 유저 이름 `furiosa001` 같은 식 (강사 지정 이름 사용)
- 우분투 버전: 퓨리오사 서버가 **Ubuntu 22.04**라서 **같은 22.04**로 맞춤
- 사용자 계정 생성 시 윈도우 사용자명이 기본값으로 따라오니 확인하고, 비밀번호는 실습용으로 단순하게 설정
- `exit` 하면 다시 PowerShell로 돌아옴

### WSL이 중요한 이유

- 실무에서도 **PyTorch/TensorFlow 코딩은 WSL에서 많이 함**
- WSL은 **윈도우 리소스(GPU 포함)를 그대로** 사용 가능

## 6. 리눅스 기본 명령어 (오늘 쓴 것)

```bash
clear                 # 화면 지우기
cd ~                  # 홈(루트) 디렉토리로 이동
cd ..                 # 상위 폴더로 이동
cd .ssh               # 폴더 이동
ls -a                 # 숨김 파일까지 모두 보기 (-a = all)
mkdir .ssh            # 폴더 생성 (make directory)
sudo apt update       # 패키지 목록 최신화 (안 해도 되지만 안전하게)
explorer.exe .        # 현재 WSL 폴더를 윈도우 탐색기로 열기 (확장자 .exe 필수, 마침표 = 현재 폴더)
```

- `.` 으로 시작하는 폴더/파일은 **숨김(설정/중요 파일)** — 그래서 `ls -a` 로만 보임
- `.` = 현재 디렉토리, `..` = 상위 디렉토리
- `explorer.exe .` 로 열면 **파일질라 같은 별도 프로그램 없이** 윈도우 탐색기로 파일 복사/이동 가능
- 방향키 ↑ 를 눌러 이전 명령어 재사용 가능 (그래도 **중요한 명령어는 메모**)
- 자주 틀리는 포인트
  - `explorer.exe` 와 `.` 사이 **띄어쓰기**
  - 현재 경로 확인 — **어느 폴더에서 명령을 치는지 항상 확인** (`.ssh` 폴더 안인지 아닌지)
  - 내 눈에 안 보이는 실수는 **옆 사람이 쉽게 찾아줌**

## 7. SSH 키로 서버 접속 (WSL 방식)

### 7-1. 순서

1. 홈에서 `.ssh` 디렉토리 생성: `mkdir .ssh`
2. 메일로 받은 키 파일(`id_rsa_숫자`, **확장자 없음**)을 `.ssh` 폴더에 복사
3. **키 파일 권한을 600으로 변경**
4. `ssh` 명령으로 접속

### 7-2. 권한 변경 (chmod)

```bash
chmod 600 id_rsa_숫자
```

- `chmod` = **ch**ange **mod**e (권한 변경)
- 600 = **나만 읽기/쓰기** 가능. 권한이 너무 열려 있으면 SSH가 키를 거부함
- 집에서 접속할 때 **이 단계를 빼먹어서 접속이 안 되는 경우가 가장 많음**

### 7-3. 접속 명령어

```bash
ssh -i ~/.ssh/id_rsa_숫자 -p 내포트번호 root@서버주소
```

| 옵션 | 의미 |
| --- | --- |
| `-i` | 사용할 키 파일(identity file) 경로 |
| `-p` | 포트 번호 (사람마다 다름) |
| `root@서버주소` | `계정@호스트` 형식 |

- 처음 접속 시 `Are you sure you want to continue connecting?` → **`yes`**
- 접속에 성공하면 **root 권한**으로 서버에 들어감 (교육용이라 root 부여)

### 7-4. 접속 안 될 때 체크리스트

| 증상 | 원인/해결 |
| --- | --- |
| **비밀번호를 물어봄** | 키가 인식되지 않은 것 → **키 경로, 파일명(`id_rsa_숫자`), 현재 폴더** 확인 |
| 접속이 거부됨 | 포트 번호 오타 (내 포트인지 확인) |
| 키를 찾지 못함 | `-i` 경로 오타, 확장자가 붙었는지 확인 |
| 접속 주소가 이상함 | 서버 주소 부분(접속 가이드 값)을 정확히 입력 |
| Windows config 오류 | 들여쓰기를 **Tab(또는 스페이스)** 으로 통일했는지 확인, 저장(Ctrl+S) 했는지 확인 |

### 7-5. 키 관리 (매우 중요)

- 키는 **개인별 개별 생성**이므로 **노출되면 끝**
- 키가 노출되더라도 피해는 파드 안에서만 발생
- **PC방 등 공용 PC에서 접속 금지 / 키를 놓고 오면 큰일**
- 집/카페 등 개인 장비에서만 접속

## 8. 퓨리오사 서버 상태 확인 명령어

```bash
furiosa-smi status      # NPU 상태(메모리 사용량, 코어/블록 활용도) — 가장 많이 사용
furiosa-smi info        # 장치 정보 (온도, 전력 등)
furiosa-smi ps          # NPU를 쓰고 있는 프로세스 확인
watch -n 1 furiosa-smi status   # 1초마다 반복 출력 → 지속 모니터링 (종료: Ctrl+C)
```

- NVIDIA의 `nvidia-smi` 에 해당하는 것이 **`furiosa-smi`**
- 터미널을 하나 더 열어 `watch` 를 켜두면 **작업하면서 메모리 점유/블록 동작을 실시간으로 확인** 가능
- Windows CMD에서 `nvidia-smi` 를 입력하면 내 노트북 GPU 상태와 **CUDA 버전**, VRAM 확인 가능
- `watch` 는 리눅스 명령어. `-n 1` 은 갱신 간격 1초

## 9. Windows 쪽에 SSH 설정 → VS Code Remote-SSH 접속

WSL을 거치지 않고 **Windows에서 바로 VS Code로 서버에 접속**하기 위한 설정.

### 9-1. 키 파일 배치

- 탐색기에서 `C:\Users\<사용자명>\` 으로 이동
- `.ssh` 폴더를 새로 만듦 (`.ssh.` 로 보이면 마지막 점은 지워짐)
- 받은 키 파일 `id_rsa_숫자` 를 그 폴더에 복사 — **확장자(.txt 등)가 붙지 않게 주의**
- 탐색기에서 **파일 확장명 표시**를 켜서 확인

### 9-2. `config` 파일 만들기

`C:\Users\<사용자명>\.ssh\config` (확장자 없는 텍스트 파일)

```text
Host furiosa-npu
    HostName 서버주소
    User root
    Port 내포트번호
    IdentityFile C:\Users\<사용자명>\.ssh\id_rsa_숫자
```

- `Host` : 내가 붙이는 **접속 별칭** (여기에 이름 아무거나 써도 됨 — 접속 시 이 이름이 표시됨)
- `HostName` : 실제 서버 주소 (접속 가이드 값 그대로)
- `User` : `root`
- `Port` : **내 포트 번호**
- `IdentityFile` : 키 파일 경로 (`id_rsa_숫자` 를 내 번호로)
- 줄 앞 들여쓰기는 **Tab**으로 통일
- `config` 파일은 **확장자 없이** 저장해야 함 (메모장은 `.txt` 가 붙기 쉬움)

### 9-3. 키 파일 권한 설정 (PowerShell)

리눅스의 `chmod 600` 에 해당하는 작업을 Windows에서는 **`icacls`** 로 수행.

```powershell
cd $env:USERPROFILE\.ssh
dir        # id_rsa_숫자, config 두 파일이 보여야 함
# (보충) 일반적인 형태 — 실제 명령은 강사가 제공한 것을 사용
icacls .\id_rsa_숫자 /inheritance:r
icacls .\id_rsa_숫자 /grant:r "$($env:USERNAME):(R)"
```

- 강사가 준 여러 줄 명령을 **복사해서 붙여넣고, 키 파일명 부분만 내 번호로 수정**
- 성공하면 **"1개 파일을 처리했습니다 / Successfully processed 1 files"** 가 출력됨
  - "0개 파일을 처리하지 못했습니다" 형태로 나오면 정상
  - 처리 실패가 나오면 파일명 오타 확인
- 윈도우 사용자 프로필 부분(`%USERPROFILE%` 등)은 **바꿀 필요 없음**

### 9-4. PowerShell로 접속 테스트

```powershell
ssh furiosa-npu
```

- `Host` 에 적은 별칭만으로 접속 가능 (포트, 키, 계정을 모두 config에서 읽음)
- 비밀번호를 물어보면 → 키 파일명/경로/번호가 틀렸다는 뜻 (**100% 키 설정 문제**)

### 9-5. VS Code Remote-SSH

1. VS Code 확장(Extensions)에서 **Remote - SSH** 설치
2. `Ctrl + Shift + P` → **`Remote-SSH: Connect to Host...`** 선택
3. 목록에서 `furiosa-npu` (config에 적은 Host 이름) 선택 → 새 창이 열림
4. 운영체제 선택 창이 나오면 **Linux** 선택
5. 설치/연결이 끝나면 **우측 하단 파란 영역에 `SSH: furiosa-npu`** 가 표시되면 성공
6. **폴더 열기(Open Folder)** → `/root` 선택 → 서버의 파일 구조가 보임

- 이후부터는 **VS Code 안에서 서버 파일을 직접 편집·실행**
- 작업용 폴더(예: `furiosa_study`)를 만들어서 사용
- Mac은 `~/.ssh` 에 같은 방식으로 키와 config를 만들면 됨 (구성 방법은 Mac용이 따로 있음)
- **앞으로의 작업 방식**: (1) WSL 터미널 접속 + (2) VS Code Remote-SSH 접속, 두 군데에서 작업

## 10. Miniconda 설치 (서버 안에서)

### 왜 Anaconda가 아니라 Miniconda인가?

- Anaconda는 **일정 규모(직원 수) 이상의 기업**에서 사용 시 **유료 라이선스 정책** 적용 → 학원/아카데미도 기업으로 볼 수 있어 라이선스 이슈 가능
- **Miniconda**는 라이선스 부담이 적고, 기능은 거의 동일하면서 **더 가볍다**

### 설치 순서

1. 공식 사이트 → **Miniconda 다운로드** → **Linux** 설치 안내 확인
2. 안내된 **`curl` 명령어**를 복사해서 터미널에 붙여넣기 (서버 터미널에서 우클릭 = 붙여넣기)
3. 내려받은 `.sh` 설치 스크립트를 실행 (`bash Miniconda3-latest-Linux-x86_64.sh`)  **(보충)**
4. 설치 후 가상환경 생성 → `퓨리오사02` 같은 이름으로 환경 분리 (오늘은 설치까지만 진행)

```bash
# (보충) 가상환경 기본 흐름
conda create -n furiosa02 python=<버전>
conda activate furiosa02
conda deactivate
```

- 파이썬 버전은 퓨리오사 SDK 요구 버전을 확인한 뒤 결정
- 강사가 이미 서버에 설치해 둔 파이썬/환경(예: 파이썬 3.x)도 있으나 **각자 새로 설치해서 사용**

## 11. 오늘의 핵심 요약 (시험/복습용)

1. **NPU = 추론 특화 칩**. GPU에서 학습(가중치 갱신) 부분을 뺀 구조 → **서비스 서버에 적합**
2. **TPS = 초당 토큰 수**, **KV 캐시 = 어텐션의 Key/Value 저장** — 둘 다 LLM 추론 성능 핵심 용어
3. **컴파일**은 학습이 아니라 **NPU용 실행 파일로 변환**하는 과정 (2시간+)
4. 서버는 **Kubernetes 파드**로 분할, 홈 폴더 밖 작업은 위험
5. **WSL 배포판은 용도별로 여러 개** 만들고, `wsl -l -v` → `wsl -d 이름` 으로 접속
6. SSH 접속 3요소: **키(`-i`) + 포트(`-p`) + 계정@주소**, 키 권한은 **`chmod 600`**
7. Windows에서는 **`.ssh/config`** 에 Host 별칭을 등록하면 `ssh 별칭` 한 줄로 접속, VS Code Remote-SSH도 같은 config 사용
8. NVIDIA의 `nvidia-smi` ↔ 퓨리오사의 **`furiosa-smi status`**, `watch -n 1` 로 실시간 모니터링
9. **Miniconda**를 쓰는 이유 = 라이선스 부담 감소 + 경량
