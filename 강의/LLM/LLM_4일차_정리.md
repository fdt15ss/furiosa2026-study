## 1. 복습: 임베딩 개념 (면접에서도 자주 나오는 핵심)

### 1-1. 왜 원핫 인코딩 대신 임베딩인가?
- 텍스트 → **토큰 단위로 자름 → 숫자로 변환**해야 모델이 계산할 수 있음.
- **원핫 인코딩의 문제**
  - 단어가 수만~수십만 개면 벡터 길이도 그만큼 → **대부분이 0인 희소(sparse) 벡터**.
  - 정수 라벨링(1, 2, 3…)은 "2는 1의 2배" 같은 **없는 크기 관계**를 만들어 버림 (범주형 데이터에 부적합).
  - 차원이 수천을 넘으면 0이 너무 많아 학습 효율이 떨어짐.
- **임베딩의 해결**: 단어를 **위치값(좌표)** 으로 바꿔서, 의미가 비슷하면 가까운 위치에 놓이게 함 (예: 왕–여왕, 남자–여자 관계).
- 구분해서 기억할 것
  - **원핫 인코딩은 Y(정답/라벨) 쪽**에서 쓰는 것
  - **임베딩은 X(입력) 쪽**에서 쓰는 것
  - 항상 "지금 X를 다루는지 Y를 다루는지" 구분하고 있어야 함.

### 1-2. 스칼라 · 벡터 · 행렬 · 텐서 / "차원"의 두 가지 뜻
| 용어 | 의미 |
|---|---|
| 스칼라 | 숫자 1개 |
| 벡터 | 스칼라의 1차원 묶음 |
| 행렬 | 2차원 |
| 텐서 | 3차원 이상 |

- **벡터 DB에서 말하는 "차원"** = 벡터 **하나** 안에 들어있는 **스칼라의 개수** (OpenAI 임베딩 기준 **1536개**).
- CNN/RNN에서 말하는 "3차원 데이터, 4차원 데이터"(텐서의 축 개수)와 **같은 말이 아니다 → 헷갈리지 말 것.**
- 벡터 스토어(Vector Store) = 이런 **벡터가 모여 있는 저장소**. 문서를 전부 벡터로 바꿔서 저장해 두고 유사도로 검색하는 것이 목적.

### 1-3. 토큰 vs 문자 vs 청크
- **청크(chunk)**: 문서를 자른 **한 덩어리** (우리가 크기를 정함).
- **토큰(token)**: 모델이 처리하는 **최소 단위**. 모델마다 기준이 다름(명확한 통일 기준 없음). 대략 "한 글자~몇 글자" 정도로만 이해.
- 텐서플로우에서 배운 `Tokenizer`(어절 단위 분할)는 **개념 학습용**이고, 실무 LLM에서는 쓰지 않음. (개념은 잊지 말 것)
- **지금 쓰는 `chunk_size`는 "문자 수" 기준**이다. (토큰 기준 분할기도 따로 존재)
- 임베딩 단위 = **청크 하나 = 벡터 하나** (글자 하나씩 벡터로 만드는 게 아님).

## 3. RAG 저장 파이프라인 : 로드 → 분할 → 임베딩 → 저장

> 비유: **"냉장고 문을 연다 → 코끼리를 넣는다 → 문을 닫는다"**
> 우리 버전: **문서를 불러온다 → 조각낸다(청킹) → 벡터화한다 → 벡터 DB에 넣는다.**

### 3-1. 문서 로드: `TextLoader`
```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader("./_data/rag_data/삼성전자.txt", encoding="utf-8")
docs = loader.load()
```
- **한글 텍스트에서 `cp949` 에러**(UnicodeDecodeError)가 나면 → `encoding="utf-8"` 지정으로 해결.
- `load()`의 결과는 **`Document` 객체의 리스트**.
  - `page_content` → **실제 텍스트 내용**
  - `metadata` → **부가 정보**(예: 파일 경로 source)

### 3-2. 폴더의 여러 파일 한 번에 불러오기 (glob + for문)
```python
import glob, os

path = "./_data/rag_data"
text_files = glob.glob(os.path.join(path, "*.txt"))   # 폴더 안 모든 txt 경로 리스트

data = []
for file in text_files:
    loader = TextLoader(file, encoding="utf-8")
    data.extend(loader.load())      # 빈 리스트에 하나씩 이어 붙이기
```
- 리스트(이터러블)를 보면 **for문**을 떠올릴 것 (개발자의 두 기본기: **조건문(if) / 반복문(for)**).
- `append`는 리스트째로 들어가고, `extend`는 **요소를 풀어서** 이어 붙임 → Document 리스트를 하나로 합칠 때 `extend`.
- 확인: `len(data)` → 파일 개수(3개), `data[0].page_content` → 첫 문서 내용.
- 문서별 글자 수 예시: 약 **8,158 / 2,049 / 1,898자**.

### 3-3. 청킹(분할): `RecursiveCharacterTextSplitter`
```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,       # 한 청크의 목표 크기(문자 수)
    chunk_overlap=100,    # 청크끼리 겹치는 구간
)
chunks = splitter.split_documents(data)
print(len(chunks))
```
- 자주 쓰는 분할기 3종: `TextSplitter` 계열 / `CharacterTextSplitter` / **`RecursiveCharacterTextSplitter`** → 모르겠으면 **Recursive를 쓰면 무난** (수업 기준 "성능 85점 이상은 나온다").
- **`chunk_overlap`을 두는 이유**: 소설처럼 문맥이 딱 300자에서 끊기지 않으므로, 앞 청크의 끝부분을 뒤 청크에 **일부 겹쳐서** 문맥 손실을 막는다.
- **Recursive**의 의미: 구분자(separators)를 **우선순위대로** 재귀적으로 시도
  - 문단 바꿈(`\n\n`) → 줄 바꿈(`\n`) → 띄어쓰기(` `) → 글자 단위
  - `CharacterTextSplitter`는 구분자가 **하나로 고정**, Recursive는 **우선순위 목록으로 변경 가능**.
- **청크가 정확히 300자가 아니라 "300자 언저리"** 인 이유: 위 구분자 경계에서 자르기 때문에 250자, 290자처럼 더 짧게 끊기는 경우가 많음(가끔 300을 넘는 경우도 있음). (직접 검색해서 원리를 찾아보라는 과제가 나왔던 부분)
- 숫자를 바꿔보며 감 잡기
  - `chunk_size=300`, `overlap=10` → 청크 **52개**
  - `chunk_size`를 키우면(예: 500) 청크 수는 **줄어든다**
  - 청크 수 = 나중에 생길 **벡터 수**
- 분할된 결과도 `Document` 리스트 → `chunks[0].page_content`, `chunks[0].metadata`, `len(chunks[0].page_content)`로 **하나씩 찍어서 확인**하는 습관.

### 3-4. 임베딩: `OpenAIEmbeddings`
```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

vec = embeddings.embed_query("삼성전자의 창업자는 누구인가요?")
print(len(vec))     # 1536
```
- **문장이 길든 짧든 결과 벡터 길이는 항상 같다** (1536). 짧은 문장, 긴 문장, 질문 모두 동일.
- 임베딩 차원은 **모델마다 고정**
  - OpenAI `text-embedding-3-small`: 기본 **1536**
  - 다른 모델(예: Qwen3 계열 등)은 차원 수가 다름 (정확한 수치는 불명확)
- `dimensions` 파라미터로 **차원을 줄일 수도** 있음(예: 5개로 줄이면 5개 출력). 다만 굳이 크게 줄일 필요는 없음.
- 정리: **청크 52개 → 벡터 52개 (각 1536차원)**.
- 여기서 `embed_query`는 `OpenAIEmbeddings` **객체가 가진 메서드(함수)**. 클래스 = 기능이 모여 있는 틀, 메서드 = 클래스 안의 함수라고 지금은 "함수"로 이해해도 충분 (파이썬 심화에서 클래스 다룰 예정).

### 3-5. 벡터 DB에 저장: `Chroma.from_documents`
```python
from langchain_chroma import Chroma

db = Chroma.from_documents(
    documents=chunks,                          # 청킹된 Document 리스트
    embedding=embeddings,                      # 사용할 임베딩 모델
    persist_directory="./_db/chroma12",        # 저장할 폴더
    collection_name="chroma_12",               # 컬렉션 이름
)
print(f"저장된 벡터 수: {db._collection.count()}")   # 52
```
- 흐름: **청크를 임베딩 → 벡터가 되어 Chroma에 저장** (그래서 저장 개수 = 청크 개수).
- `persist_directory` = **디스크에 영구 저장**되는 경로. 폴더에 `chroma.sqlite3` 등이 생김.
- **컬렉션(collection)** = MySQL의 **테이블** 같은 개념 (DB 안에서 묶음 단위). 수업에서 처음엔 `chroma11`, 다음엔 `chroma12`로 이름을 바꿔 가며 실습.
- ⚠️ **같은 셀을 여러 번 실행하면 같은 데이터가 중복으로 계속 쌓인다**
  - 실제로 4번 실행 → 52×4 = **208개**로 늘어남 (용량도 증가, 검색 속도 저하 가능).
  - 해결: ① 실습 중에는 **DB 폴더를 지우고 다시 생성**, ② 실무에서는 **ID/인덱스로 중복을 막는 방법**(추후 학습).
  - 에러가 난 경우에만 한 번 더 실행할 것. "한 번만 실행"이 원칙.
- (참고) 데이터가 아주 크면 중복 관리가 필수, 지금 작은 데이터 실습에선 생략.

## 4. 저장된 DB 불러오기 · 유사도 검색 · 리트리버

### 4-1. 저장된 DB 불러오기
```python
db = Chroma(
    persist_directory="./_db/chroma12",
    embedding_function=embeddings,     # ← 저장할 땐 embedding, 불러올 땐 embedding_function
    collection_name="chroma_12",
)
```
- **이미 저장돼 있으니 문서 로드/청킹/저장 코드는 필요 없음** (주석 처리하거나 삭제).
- 대신 **같은 임베딩 모델은 반드시 다시 지정**해야 함 (질문을 같은 방식으로 벡터화해야 비교 가능).
- **파라미터 이름 주의**: 저장할 때는 `embedding`, 불러올 때는 `embedding_function`.
- 내용 확인: `db.get()`

### 4-2. 유사도 검색: `similarity_search`
```python
results = db.similarity_search("삼성전자의 창업자는 누구인가요?", k=2)
for r in results:
    print(r.page_content[:50])
```
- 동작 순서
  1. 질문을 **같은 임베딩 모델로 벡터화**(1536차원)
  2. DB의 52개 벡터와 **코사인 유사도(각도 기준)** 로 비교
  3. 유사도가 높은 **상위 k개 청크**를 `Document`로 반환
- `k`의 **기본값은 4** → 안 쓰면 4개가 나옴.
- 코사인 유사도 = **거리가 아니라 "각도"** 를 보는 방식 (2일차 복습).
- 결과 안의 `page_content`(내용), `metadata`(경로 등)를 확인.

### 4-3. 리트리버(Retriever) — RAG의 "검색기"
```python
retriever = db.as_retriever(search_kwargs={"k": 2})
docs = retriever.invoke("삼성전자의 창업자는 누구인가요?")
for d in docs:
    print(d.page_content[:50])
```
- **RAG에서 Retriever = 검색 담당.** 인터넷 검색이 아니라 **우리가 만든 벡터 스토어에서 검색**.
- LCEL(`|` 파이프 문법)로 체인을 이을 때 **맨 앞 단계가 검색기**가 됨 (내일 이어서 진행).
- `.invoke()` = "실행해라(호출)" 메서드.
- 이런 메서드명을 다 외울 필요는 없고, **헷갈리면 바로 찍어보고(print), 검색하고, 메모해 둘 것.**

### 4-4. f-string 출력 팁
```python
print(f"저장된 벡터 수: {db._collection.count()}")
```
- `{ }` 안에 변수/식을 직접 넣을 수 있어서 출력할 때 자주 사용.

## 5. 오전 복습 (딥러닝): 시계열 데이터에 `Conv1D`

> 예나(Jena) 기온 시계열 데이터를 LSTM 대신 합성곱으로 처리해 보는 실습.

- **3차원 시계열 데이터** `(샘플 수, 타임스텝, 특성 수)`는 RNN만이 아니라 **`Conv1D`** 로도 처리 가능.
- `Conv1D(filters=10, kernel_size=2)` → 커널이 **타임스텝 방향으로 2개씩** 훑으며 특성을 뽑음 (Conv2D의 `(2,2)`와 달리 사실상 `(2,1)`).
- **차원**: 입력 3차원 → 출력도 3차원(타임스텝 축이 줄어들 수 있음).
- **Dense로 이어붙이기 전에** 3차원을 풀어줘야 함 → `Flatten()` 또는 `GlobalAveragePooling1D()` (둘 중 취향대로).
- **에러 해결 팁**
  - 데이터가 작아서 타임스텝이 계속 줄어 에러가 나면 → **`padding="same"`** 지정.
  - 에러가 나면 **shape을 찍어가며 한 줄씩 디버깅**(에러가 많이 나는 게 좋은 공부).
- 이전 실습처럼 Conv2D로 억지로 바꾸지 않아도 되고, **작은 데이터에서는 Conv1D가 더 좋은 경우도 많음.**
- 선택지 정리: 시계열 데이터를 받았을 때 **RNN/LSTM 계열 + Conv1D (+ 둘을 합친 구조)** 모두 선택 가능.
- 실습 목표: **이전 LSTM 모델의 성능을 Conv1D로 따라잡기**, 그리고 **학습 시간 차이도 비교**.
- 새 모델을 만들 땐 **이전 모델의 성능을 기준점으로 삼고** 개선 목표를 분명히 잡을 것 (막연히 "더 좋게" X).
- 주의사항 복기
  - 회귀에서 출력층에 `softmax`를 쓰지 않고 **`Dense`로 구성**
  - 데이터 reshape을 바꿀 땐 **split 단계부터** 일관되게 바꿔야 함 (순서·값이 바뀌면 안 됨).

---

## 6. 핵심 요약 & 내일 예고

### ✅ 오늘의 핵심 한 줄
**"문서를 불러와서(Load) → 청킹하고(Split) → 벡터화해서(Embed) → 저장한다(Chroma). 불러올 땐 저장된 DB를 그냥 연결하면 된다."**

### 체크리스트
- [ ] 원핫 인코딩의 문제(희소, 가짜 크기 관계)와 임베딩의 해결을 설명할 수 있다
- [ ] 벡터 DB의 "차원" = 벡터 하나 안의 스칼라 개수(1536)임을 설명할 수 있다
- [ ] `TextLoader(encoding="utf-8")`, `glob` + `for` + `extend`로 여러 파일을 읽을 수 있다
- [ ] `RecursiveCharacterTextSplitter`의 `chunk_size`, `chunk_overlap` 의미를 설명할 수 있다
- [ ] 청크 수 = 벡터 수 = DB에 저장되는 개수임을 안다
- [ ] 저장(`Chroma.from_documents`)과 불러오기(`Chroma(... embedding_function=...)`)의 차이를 안다
- [ ] 같은 저장 코드를 반복 실행하면 중복 저장됨을 안다
- [ ] `similarity_search(k=...)` 기본값(4)과 `as_retriever`로 검색기를 만드는 법을 안다

### 퀴즈 복습
- Q. 벡터 DB에 들어가는 벡터의 단위는? (글자 1개 / **청크 1개**) → **청크 1개**

### 내일 예고 (강사 안내)
- 검색(Retriever) 결과를 **LLM에 연결해 답변까지 생성(RAG 체인)**
- 임베딩 모델 비교(OpenAI 외 다른 모델/로컬 모델 후보 언급)
- 이후 챗봇 형태로 확장

# 🗂️ 특별 탭: AI 산업 이야기

> 오전에 **보조강사님 소개 · 질의응답** 시간에 나온 AI 업계/커리어 관련 이야기입니다.
> ⚠️ 대부분 **강사 개인의 경험과 견해**이므로, 참고용으로 읽고 본인의 판단으로 걸러서 활용하세요.

## A. 교육 일정 / 운영 안내
- 교육 시작 후 **약 한 달**이 지났고, 이제 **본격적인 개념 수업**에 들어감. 시기에 따라 **미니 프로젝트**도 진행 예정.
- **보조강사님이 오늘부터 합류** → 수업 중 막힐 때 손을 들면 도와주고, 실습 시간에 **1:1 짧은 면담**(배경 파악 후 맞춤 도움)을 진행할 계획.
- 보조강사님 원칙: **메인은 강사님 설명에 맞추고**, 이해가 어려운 부분은 눈높이에 맞춰 보충.
- 남은 기간(약 2~3개월)과 **체력 관리** 당부: "컨디션이 곧 실력". 한 번 크게 아프면 공부한 게 소용없어지므로 건강부터 챙기기.

## B. 보조강사님 커리어 경로 (요약)
- **기획자(PM)** 로 시작 → 데이터 분석/빅데이터 → 머신러닝·딥러닝 **강사(KDT 과정, 약 3년)** → 현재는 **에이전트 중심**으로 프로젝트와 강의를 병행.
- 전환 계기: 데이터 분석만으로는 한계를 느낌 → AI → LLM → **에이전트**로 시장이 빠르게 이동.

## C. 업계 변화에 대한 관찰
- **데이터 분석 직무의 변화**: 일부 대기업/게임사에서 분석 조직이 축소·재편되어 다른 직무로 이동한 사례를 언급 (구체적 사례는 강사 발언 기준).
- **채용 시장**: "AI 서비스 개발자"라고 해도 이제는 **ML/DL보다 에이전트 개발 경험**을 기대하는 경우가 많다는 체감.
- **개발 속도의 변화**: 예전에 2~3개월 걸릴 일을 에이전트/바이브 코딩으로 **훨씬 짧게** 만들 수 있게 됐다는 사례(대표님들과의 대화).
- **바이브 코딩의 한계선**
  - **MVP 제작·기본 운영·배포**까지는 충분히 가능
  - **대규모/엔터프라이즈 운영, 보안 책임**이 붙으면 바이브 코딩만으로는 어렵다
- **AGI / ASI에 대한 개인 의견**
  - AGI의 **정의 자체가 아직 불명확**
  - 에이전트 덕분에 **AGI에 가까운 수준은 빨리 올 수 있어도, 초지능(ASI)까지는 큰 벽이 있을 것**이라는 견해
  - (정설이 아니라 개인 견해)
- **현재는 과도기**: 변화가 너무 빨라 직무·역할 경계가 계속 흔들리는 시기.
- **API 의존 이슈**(메인 강사님 언급): OCR 등 많은 서비스가 사실상 "**기승전 API**"가 되어, 폐쇄망·보안 민감 기업에서는 API 사용을 꺼림 → 외부로 데이터가 나가는 문제 때문에 **로컬/자체 모델(올라마 등) 수요**가 생긴다는 맥락. (세부 내용은 음성 인식 불명확)

## D. 포트폴리오 · 프로젝트 주제 선정
**Q. 프로젝트 주제를 정하기 어렵다. 어떻게 고르면 좋을까?**
- 먼저 **목적**을 구분:
  1. **학습 / 포트폴리오 목적**
     - 아이디어의 참신함보다 **"내가 가진 기술 + 장점 + 내가 잘 아는 도메인"** 을 붙이는 게 핵심.
     - 예) 직업훈련 강사 경력이 있다면 → 그 현장의 **페인포인트**를 에이전트 기술로 푸는 프로젝트.
     - 지금 가장 **수요가 많은 기술(에이전트 등)** 을 구현하는 데 에너지를 쓰기.
     - 아이디어가 막히면 AI에게 "내 배경은 ○○, 이 기술을 해보고 싶다"고 물어보는 것도 방법(단, 그대로 믿지 말고 본인 도메인과 연결).
  2. **비즈니스/사업화 목적**
     - **전통 비즈니스**: 시장 리서치 데이터 기반으로 도출.
     - **신규 비즈니스**: **유저 리서치 → 니즈·페인포인트 발굴 → 내 기술로 해결 가능한 것** 연결.
- **불완전 정보의 시대 → 애자일**: 시장이 너무 빨리 변하므로 길게 분석하기보다 **작게 만들어 빠르게 시장 검증 → 계속 수정**.
- 기획자의 역할이 확장됨: 이제는 **프로토타입/디자인까지 직접** 만드는 방향.

## E. 채용 / 면접 관점 (강사 개인 의견)
- 면접관 입장에서 보고 싶은 것 → **적응력**: "세상의 변화를 따라왔고, 앞으로도 따라갈 수 있다"는 증거(포트폴리오·경험).
- 면접관이 AI에 깊지 않을 수도 있으므로, 기술 나열보다 **변화에 적응해 온 과정**을 보여주는 어필도 효과적이라는 조언.
- **자격증**: 실무에 직접 도움이 된다기보다 **학습 목표/체계적 보충**용으로 유용. 부족한 부분은 **교재·자격증·사이드 프로젝트·프리랜서 경험**으로 메우며 경력을 쌓았다는 경험담.
- 압축된 커리큘럼(학부 2~4년 분량을 단기 과정으로)이라 **다 이해 못 하는 게 정상** → 개인 학습으로 보충 필요.

## F. Q&A: "AI 개발 방식 세 가지 유형, 어느 쪽이 좋은가?"
질문자가 현업에서 본 세 유형:
1. AI를 아예 안 쓰는 개발자
2. AI를 쓰되 **코드를 완벽히 이해**하며 조금씩 쓰는 개발자
3. **코드를 직접 보지 않고**, 여러 AI(Claude / ChatGPT / Gemini 등)로 **교차 검증 + 다양한 테스트**를 통해 빠르게 만드는 개발자

**강사님 답변(개인 견해)**
- 기업(비즈니스) 관점에서는 **3번을 선호**하는 경향. 지금 목표는 코딩 대회가 아니라 **빠르게 서비스를 내고 검증**하는 것.
- AI가 만든 코드를 **AI가 검증**하게 하고, **사람은 검증 구조·정책(누가 누구를 어떻게 검증하고 어떤 순서로 돌릴지)** 을 설계. 에이전트를 배우는 이유도 이것.
- 다만 **보안 등 중요한 영역은 사람이 한 번 더 확인**하고 의사결정은 사람이 함.
- 본인도 예전엔 2번이었지만, 3번 유형이 **에이전트 이해와 적응력**이 좋다고 판단하게 됐다고 함.

> 📝 정리자 메모: 위는 한 강사의 견해입니다. "코드를 이해하는 능력"과 "검증 구조를 설계하는 능력"은 대체 관계가 아니라 **서로 보완**되는 면이 있어서, 직무·조직 성격(보안/안정성 요구 수준)에 따라 균형이 달라질 수 있다는 점은 열어 두고 보세요. 수업에서도 "처음 공부할 땐 코드를 이해하는 게 필요하다"고 같이 언급됨.

## G. 비개발 직군(기획자 등)과 일반 학습자를 위한 조언
- **제너럴리스트 선호 흐름**: 예전의 "T자형 인재"에서 더 나아가, **기획·설계·디자인·개발·배포·운영 전 과정을 한 번씩 직접 만들어 보는 경험**이 중요해졌다는 의견.
- **개념 이해가 우선**: 코딩 실력에 너무 걱정하지 말고 "이게 이렇게 돌아가는구나"를 이해하면 충분 (논리적 사고·알고리즘 이해를 위해 코딩 학습 자체는 필요).
- **소프트 스킬의 중요성**: 예전엔 **사람 관리** 역량, 이제는 **에이전트 관리** 역량.
  - 둘 다 핵심은 **명확한 소통 + 그 일에 대한 이해** (프롬프트 엔지니어링도 결국 구조화된 소통).
- **기획 스타일 팁**: 상위 기획(왜/무엇을) 없이 상세 기획부터 하면 나중에 꼬이기 쉬움 → **"왜 해야 하는가"의 근거와 방향을 먼저 잡고(데이터 드리븐, 바텀업) 에이전트와 같이 개발**하면 AI가 맥락을 잃지 않는다는 경험담.
