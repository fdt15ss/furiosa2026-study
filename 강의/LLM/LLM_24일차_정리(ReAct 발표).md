## 0. 한눈에 보는 흐름

| 논문 | 핵심 아이디어 | 해결한 문제 | 남은 문제 → 다음 논문의 출발점 |
|---|---|---|---|
| **CoT** (2022) | 예시에 **풀이 과정**을 넣는다 | 다단계 추론 문제에서 정답률이 낮음 | 머릿속 지식만 써서 **사실을 지어냄(환각)** |
| **ReAct** (2022~23) | **Thought → Action → Observation** 반복 | 모르면 **외부 도구로 찾아봄** → 환각 감소 | 틀려도 **다음 시도에서 배우지 못함** |
| **Reflexion** (2023) | 채점 → **언어로 반성** → 메모리에 저장 후 재시도 | 실패 경험을 다음 시도에 반영 | **채점(평가자)이 틀리면** 반성도 틀림 |

**공통점**: 세 논문 모두 **모델 가중치를 다시 학습시키지 않고**, 프롬프트/일하는 방식만 바꿈.
→ "생각하고(CoT) · 도구를 쓰고(ReAct) · 기억한다(Reflexion)" = 우리가 수업에서 만드는 에이전트의 구성요소.

## 1. 기본 개념 정리

### 1-1. 파인튜닝 vs 프롬프트 엔지니어링
| 구분 | 파인튜닝 | 프롬프트 엔지니어링 |
|---|---|---|
| 가중치 | **갱신함** (파라미터 수정) | **고정** |
| 방법 | 추가 데이터로 학습 | 입력(프롬프트) 형식만 조정 |
| CoT/ReAct/Reflexion | ❌ | ✅ 여기에 해당 |

### 1-2. LLM이 답을 만드는 방식
- LLM은 **컨텍스트를 읽고 다음 토큰 1개를 예측** → 그 토큰을 컨텍스트 끝에 붙여서 다시 예측 → 반복 (자기회귀, autoregressive)
- 그래서 "답 앞에 어떤 텍스트가 먼저 생성되느냐"가 답의 품질을 바꿈 → CoT의 원리

### 1-3. Zero-shot / One-shot / Few-shot (교수님 질문 ⭐)
"샷(shot)" = 모델에게 주는 **예시의 개수**

| 방식 | 설명 | 예 |
|---|---|---|
| **Zero-shot** | 예시 없이 질문만 | `질문: ... 답:` |
| **One-shot** | 예시 1개 + 질문 | `Q1/A1 → 질문` |
| **Few-shot** | 예시 여러 개 + 질문 | `Q1/A1, Q2/A2, Q3/A3 → 질문` |
| **Zero-shot CoT** | 예시 없이 "단계적으로 생각해" 한 줄 추가 | `Let's think step by step.` |

> 💡 교수님: "이런 간단한 것도 면접 가면 떨려서 생각 안 난다. **서서, 말로** 계속 연습해야 바로 대답이 나온다."

```python
# Few-shot vs Few-shot CoT 프롬프트 비교
few_shot = """
Q: 사과 5개가 있는데 2개를 먹었다. 몇 개 남았나?
A: 3개

Q: 커피 4,500원, 케이크 3,500원을 10,000원으로 샀다. 거스름돈은?
A:"""

few_shot_cot = """
Q: 사과 5개가 있는데 2개를 먹었다. 몇 개 남았나?
A: 처음 5개에서 2개를 먹었으므로 5 - 2 = 3. 답은 3개.

Q: 커피 4,500원, 케이크 3,500원을 10,000원으로 샀다. 거스름돈은?
A:"""   # 모델도 풀이를 따라 쓰면서 4,500+3,500=8,000 → 10,000-8,000=2,000 에 도달

zero_shot_cot = "Q: 커피 4,500원, 케이크 3,500원을 10,000원으로 샀다. 거스름돈은?\nA: Let's think step by step."
```

> 발표 예시: Few-shot은 중간 계산 없이 **4,000원(오답)**, CoT는 풀이를 거쳐 **2,000원(정답)**.

## 2. Chain-of-Thought (CoT)

### 2-1. 핵심
- 표준 프롬프팅: `입력 X → 출력 Y`
- CoT: `입력 X → **추론 과정(rationale)** → 출력 Y`
- 사람이 문제 풀 때 **풀이를 적듯이**, 예시(exemplar)에 풀이를 넣어 모델도 풀이를 쓰게 함

### 2-2. 실험 결과 (발표 내용)
- **PaLM 540B**, 초등 수학 문장제 **GSM8K**: 정답률 약 **18% → 57%**
  - 추가 학습 없이 당시 파인튜닝 최고 기록도 넘음
- 상식 추론(CSQA 등)·기호 추론에서도 향상. 단, 쉬운 객관식(CSQA)은 큰 차이 없음
- **Ablation(하나씩 빼보기) 실험**
  - 수식만 쓰게 하기 ❌
  - 길이(토큰 수)만 늘리기 ❌
  - 답 **뒤에** 풀이 쓰기(answer first) ❌
  - → **답 이전에 의미 있는 추론 과정**이 있어야만 효과 있음

### 2-3. 창발적 능력 (Emergent Ability) — 교수님 질문 ⭐
- CoT 효과는 **약 100B(1,000억) 파라미터 이상** 큰 모델에서 뚜렷하게 나타남
- 작은 모델(예: 8B)은 **풀이 자체의 질이 낮아서** 오히려 성능이 정체되거나 떨어짐
- 이렇게 **규모가 커지면서 갑자기 나타나는 능력** = 창발적 능력
- 관련 개념: **Grokking** — 같은 데이터로 학습을 계속하다 어느 순간 갑자기 일반화 능력이 생기는 현상 ("해골물을 먹은 순간" 😄)

> ❗ 교수님 지적: "요즘 8B 모델도 잘 하는데 왜 100B 이상이어야 하냐?" → **당시(2022) 모델 기준**의 결과라는 맥락을 설명할 수 있어야 함. 슬라이드에 넣은 내용은 반드시 답할 수 있게 준비.

### 2-4. 한계
- 모델 **내부 지식만** 사용 → 존재하지 않는 사실도 그럴듯한 추론으로 만들어냄 (**환각**)
- 토큰 사용량·응답 시간 증가
- 큰 모델에서만 효과

## 3. ReAct (Reasoning + Acting)

### 3-1. 핵심 구조: Thought → Action → Observation 루프
```
Question
  ↓
Thought  : 무엇을 알아야 하지? (계획, 상태 요약)
Action   : search[...], lookup[...], finish[...]   ← 외부 도구 호출
Observation : 도구 실행 결과 → 컨텍스트에 누적
  ↓ (답이 나올 때까지 반복)
Finish[정답]
```
- 모델 바깥의 행동 결과(Observation)가 **다시 컨텍스트에 쌓임**
- 위의 과정 기록 = **trajectory(로그)**

### 3-2. 논문 예시 (HotpotQA)
> Q. "Apple Remote 말고, Apple Remote가 원래 조작하던 프로그램을 조작할 수 있는 다른 기기는?"

| 방식 | 동작 | 결과 |
|---|---|---|
| Standard | 바로 답 | iPod ❌ |
| CoT (생각만) | Apple TV용이라고 잘못 기억 | iPhone, iPad ❌ |
| Act (행동만) | 검색은 하지만 정리 못 함 | yes ❌ |
| **ReAct** | Front Row용임을 확인 → 재검색 | **키보드 기능키 ✅** |

다른 팀 예시들:
- 넷플릭스 1위 작품 주연배우 나이 → 생각만: 학습 당시 정보로 추정(오답) / 행동만: 1위 작품만 찾고 멈춤 / ReAct: 1위 → 주연 → 나이까지 연결
- 자동차 시동 안 걸리고 딸깍 소리 → CoT: "배터리 전압 문제" 추정으로 끝 / ReAct: 배터리 전압·단자 상태를 실제로 확인 후 결론

### 3-3. 실험 결과
| 벤치마크 | 결과 |
|---|---|
| HotpotQA (지식 QA) | ReAct 27.4% < CoT 29.4% (살짝 낮음) |
| HotpotQA, **ReAct + CoT-SC 결합** | **35.1%** (가장 좋음) |
| FEVER (사실 검증) | ReAct가 CoT보다 높음 |
| ALFWorld (텍스트 게임) | ReAct **71%** vs Act-only 45% |
| WebShop (쇼핑) | ReAct **40%** vs 모방/강화학습 모델 28.7% |

**실패 원인 분석 (사람이 직접 확인)**
- CoT 오답의 **56%가 환각** 때문 / ReAct는 환각으로 인한 오답 **0%**
- ReAct 오답의 **47%는 추론 오류** — 검색 반복 루프에 갇히거나, 엉뚱한 검색 결과에 끌려감

> ⚠️ "환각 0%"는 **해당 데이터셋 분석에서** 0%라는 뜻. ReAct도 환각이 완전히 없는 것은 아님 (발표자 답변).

### 3-4. 왜 HotpotQA에서 CoT가 더 높았나? (질의응답 ⭐)
- CoT는 상식 수준 질문을 **머릿속 지식만으로도** 풀 수 있음
- ReAct는 검색 결과가 엉뚱하거나 반복되면 틀림 (정형화된 구조라 유연성 ↓)
- 대신 ReAct는 **지어낸 답이 없고, 검색 근거가 남음** → 두 방식은 경쟁이 아니라 **상호 보완**

### 3-5. 구현 팁 (발표에서 나온 실습 포인트)
1. **Observation도 출력**하게 해야 루프 동작을 확인할 수 있음 (원래 수업 코드는 Action만 출력)
2. 모델이 **도구를 한꺼번에(병렬) 호출**하면 풀이 과정이 꼬일 수 있음 → **하나씩 순차 실행**
   - 예: `6912` 결과를 보고 그 값으로 다음 계산 / `4821 ÷ 0` → 에러를 관찰하고 계산하지 않은 이유를 설명
3. **덜 친절한 도구**에서 ReAct의 장점이 드러남
   - "오후 2시 서울역 출발" → 시간표에서 `"2시"` 검색 실패 → 관찰 후 `"14시"`로 키워드 수정 → 16:48 도착 정답
4. **최대 반복 횟수(max_iterations)** 를 반드시 제한 (무한 검색 루프 방지)

### 3-6. 최소 ReAct 루프 예제 (Python)
```python
import re

def calculator(expr: str) -> str:
    try:
        return str(eval(expr, {"__builtins__": {}}))
    except ZeroDivisionError:
        return "Error: division by zero"

TOOLS = {"calculator": calculator}

def react_loop(llm, question: str, max_steps: int = 5):
    context = f"Question: {question}\n"
    for step in range(max_steps):
        out = llm(context)                 # Thought + Action 생성
        context += out + "\n"
        print(out)

        if "Finish[" in out:               # 종료 조건
            return re.search(r"Finish\[(.*?)\]", out).group(1)

        m = re.search(r"Action: (\w+)\[(.*?)\]", out)
        if m:                              # 도구는 한 번에 하나씩 실행
            tool, arg = m.groups()
            obs = TOOLS[tool](arg)
            print(f"Observation: {obs}")   # ← Observation도 꼭 출력
            context += f"Observation: {obs}\n"
    return "max_steps 초과 - 실패"
```

## 4. Reflexion

### 4-1. 핵심 구조
```
┌──────────┐   trajectory   ┌────────────┐   성공/실패   ┌─────────────────┐
│  Actor   │ ─────────────▶ │ Evaluator  │ ───────────▶ │ Self-Reflection │
│ (ReAct)  │                │  (채점자)   │              │  (반성문 작성)   │
└──────────┘                └────────────┘              └────────┬────────┘
     ▲                                                            │
     └──────────── 장기 메모리(반성문 목록)를 다음 컨텍스트에 추가 ◀──┘
```
- **Actor**: 행동(ReAct로 문제 풀이)
- **Evaluator**: 성공/실패 채점 (= **Test Oracle**)
- **Self-Reflection**: 실패 원인을 **언어로** 성찰
- **Memory**: 반성문을 에피소드 메모리에 저장 → 다음 시도에 반영
- 반복할 때 바뀌는 건 **반성문 목록뿐**, 모델 가중치는 그대로

### 4-2. "말로 하는 강화학습 (Verbal RL)"
| 구분 | 기존 강화학습 | Reflexion |
|---|---|---|
| 보상 처리 | 보상으로 **가중치 업데이트** | 보상을 **언어 피드백**으로 바꿔 저장 |
| 학습 | 파라미터 변화 | 프롬프트(메모리)만 변화 |
| 비유 | — | 바둑에서 진 뒤 복기, 시험 0점 받고 "다음엔 이렇게" |

### 4-3. 단기 메모리 vs 장기 메모리 (질의응답 ⭐)
| 메모리 | 내용 | 이유 |
|---|---|---|
| **단기** | 이번 시도의 전체 이력(trajectory) | 현재 시도 진행용 |
| **장기** | 왜 실패했는지 요약한 **반성문** | 이력을 다 넘기면 컨텍스트·비용 폭증 → 요약만 유지 |

- 반성문을 너무 많이 쌓으면 **잘못된 교훈도 계속 남아** 추론을 방해 → 논문도 최근 몇 개(1~3개)만 유지
- 많이 실행하는 것보다 **무엇이 잘못됐는지 정확히 잡는 것**이 중요

### 4-4. 실험 결과
| 벤치마크 | 결과 |
|---|---|
| HumanEval (코딩 164문제, pass@1) | Reflexion **91%** vs GPT-4 단독 80% |
| ALFWorld | **134개 중 130개** 성공 (ReAct만 쓰면 약 75%에서 정체) |
| MBPP (Python) | 오히려 낮음 → **평가자가 틀린 답을 맞다고 판정(false positive)** |

### 4-5. 예시
- 회의실 예약(8명, 프로젝터·화이트보드 필요): 1차에 10인실 선택 → 프로젝터 없어 실패 → 반성 "인원과 **필수 장비를 먼저** 확인" → 2차 성공
- 경유 열차: 대전에서 1시간 머문 뒤 다음 열차 → 1차에 서울역 기준으로 검색해 실패 → 반성 "경유 후에는 **경유지 기준**으로 검색" → 2차 성공
- 자동차: 배터리 충전 후에도 딸깍 → 반성으로 전압 말고 **스타트 모터/솔레노이드** 문제로 전환

### 4-6. 한계
1. **Test Oracle(평가자)이 틀리면** 오염된 반성이 생기고 계속 반복됨 → 그래서 **정답이 명확한 테스트 기반(코드 테스트, 빌드 등)** 에서만 의미가 큼
2. **작은 모델**은 자기 채점/성찰 품질이 낮아 잘 안 됨 (팀 실습: 8B 모델로 **5번 시도 모두 실패**)
3. 메모리 용량 한계, 오래된 메모리 활용 어려움
4. 비용·응답 시간 증가 → **재시도 횟수 제한, 필요한 기록만 유지** 필요

> ❗ 교수님 질문: "5번 모두 실패했다는 **실패 기준**이 뭐냐?" → 정량 기준(예: "가나다 순서로 14단어 문장" 조건을 단어 수·순서로 검사)을 명확히 말할 수 있어야 함. "논리적으로 안 맞으면 실패"는 결국 **주관적 기준**이라는 지적.

### 4-7. Reflexion 루프 예제 (Python)
```python
def reflexion(llm, task, evaluator, max_trials=5, mem_size=3):
    long_term_memory = []                       # 반성문 목록

    for trial in range(1, max_trials + 1):
        reflections = "\n".join(long_term_memory[-mem_size:])
        prompt = f"과거 반성:\n{reflections}\n\n과제: {task}"
        answer = react_loop(llm, prompt)        # Actor

        ok, feedback = evaluator(answer)        # Evaluator (테스트 코드 등 명확한 기준!)
        print(f"[trial {trial}] {'성공' if ok else '실패'}: {feedback}")
        if ok:
            return answer

        reflection = llm(                       # Self-Reflection
            f"과제: {task}\n답: {answer}\n실패 이유: {feedback}\n"
            "다음 시도에서 고칠 점을 한두 문장으로 써라."
        )
        long_term_memory.append(reflection)
    return None   # max_trials 초과 → 실패 처리
```

## 5. 세 방식, 언제 쓰나?

| 상황 | 적합한 방식 |
|---|---|
| 필요한 정보가 **문제 안에 다 있음** (계산, 논리) | **CoT** |
| **최신 정보·외부 데이터**가 필요함 | **ReAct** |
| 성공/실패를 **테스트로 명확히 판정** 가능 + 여러 번 시도 가능 | **Reflexion** |

- 세 방식 모두 추가 추론·도구 호출·자기반성 **비용**이 듦 → 필요한 기록만 남기고, 재시도 횟수 제한
- 중요한 것: "어떤 방식이 무조건 좋다"가 아니라 **문제 유형을 먼저 파악하고 방법을 고르는 것**
- 실제 사례: Cognition의 **Devin** — 코드를 짜고, 스스로 오류를 진단해 다시 고치는 Reflexion 계열 구조

### 질의응답에서 나온 개념 구분
- **환각(Hallucination)** vs **추론 오류**: 교수님은 "같은 말 아니냐?"고 지적
  - 환각 = 없는 사실을 **지어냄**
  - 추론 오류 = 사실은 맞게 가져왔는데 **연결·판단을 잘못함** (ReAct의 반복 루프 등)
  - → 발표할 때 이 차이를 **명확한 한 문장**으로 말할 수 있어야 함
- **HotpotQA vs FEVER**: HotpotQA = 여러 문서를 건너 추론하는 멀티홉 QA / FEVER = 주장의 사실 여부 검증
- **PaLM 540B**: Google의 5,400억 파라미터 LLM

### 팀 실습에 대한 교수님 피드백
- "리만 가설 최신 연구" 에이전트(Qwen3 8B + 날짜 비교 툴 + 웹서치) → "그냥 **뉴스 검색이랑 뭐가 다르냐?** 엔비디아 오늘 주가 알려줘와 차이가 뭐냐" → 시작은 거창한데 결과는 단순 검색
  - 👉 실습 예시는 **ReAct의 장점(관찰 후 행동 수정, 다단계 도구 연결)이 드러나는 문제**로 설계할 것
- "논문 설정 그대로, 모델만 바꿨다(Llama 3.1 8B)" → **논문 내용과 실습이 어떻게 매칭되는지** 구체적으로 설명하거나, 아니면 그 슬라이드는 빼라

## 6. 퓨리오사(Furiosa) NPU 내부 구조 발표

### 6-1. 최적화 원리
- NPU는 **추론(inference) 전용**
- 신경망 연산 `Y = XW + B` 에서 추론 시 **X(입력)만 변하고 W(가중치)·B(바이어스)는 고정**
- → W, B는 레지스터에 **고정**해두고 X만 빠르게 공급하면 빠르다!

### 6-2. 메모리 계층
| 메모리 | 역할 |
|---|---|
| **HBM3 (48GB)** | 모델 전체를 미리 올려두는 곳. 직접 연산에 쓰이지 않음. 상대적으로 저렴 |
| **SRAM (DM, Data Memory)** | 연산 직전 필요한 부분만 복사. 매우 빠름. 슬라이스/레인 단위로 분할 |
| **TRF** (Tensor Register File) | **고정된 가중치 W** 저장 → 행렬곱 등 주요 연산 |
| **VRF** (Vector Register File) | **바이어스, ReLU** 등 벡터 연산 관련 정보 |

- 레지스터가 비싼 이유: 연산 회로 바로 옆에 붙어 동작하는 초고속 저장소라 면적·비용이 큼

### 6-3. 하드웨어 계층 & 컴파일 옵션
- 주소처럼 분할: **칩 → 클러스터 → PE → 슬라이스** ("서울시 영등포구 ..." 처럼)
- 실제 연산은 **슬라이스**에서, 슬라이스는 **8개 레인**으로 나뉨
- 컴파일 시 **칩 개수, PE 개수** 지정 가능
  - 예: 칩 2개 × 칩당 PE 4개 = **총 8 PE**

### 6-4. 데이터 이동 경로
```
PC RAM → (모델 로드) → HBM3 → (DMA) → SRAM(DM)
       → Fetch → Collect(위치 정렬) → TRF / VRF
       → Contraction Engine (W·X 계산) → +Bias, ReLU → DM으로 다시 저장
```
- **DMA (Direct Memory Access)**: CPU 개입 없이 큰 메모리 덩어리를 한 번에 복사

### 6-5. 타일링 & 더블 버퍼링
- **타일(Tile)**: 한 번에 적재하는 데이터 단위 / **타일링**: 타일 크기를 정하고 나누는 작업
- **더블 버퍼링(핑퐁 버퍼)**: 연산하는 동안 다음 데이터를 미리 적재 → 적재와 연산을 겹쳐서 대기시간 제거
- 이 배치·전송 순서·중첩 실행을 **컴파일러가 자동으로** 결정

### 6-6. Eager 모드 vs Compile 모드
| 모드 | 동작 | 속도 |
|---|---|---|
| **Eager** | 연산 하나마다 NPU 계산 → CPU로 결과 → 다시 NPU 요청 | CPU↔NPU 왕복 많음 → 느림 |
| **Compile** | 전체 그래프를 분석해 NPU 안에서 한 번에 실행 | 왕복 최소화 → 빠름 |

```python
# PyTorch 2.x 개념으로 이해하기 (torch.compile과 같은 아이디어)
model_eager = model                          # 한 줄씩 즉시 실행
model_compiled = torch.compile(model)        # 그래프 전체를 최적화해 한 번에 실행
```

### 6-7. 컴파일 산출물 & Dry-run
- 모델 → 컴파일러 → **중간 기계어 수준 파일(EDF)** 여러 개 → 묶어서 최종 실행 파일 생성
- **dry-run 옵션**: 실제 컴파일은 하지 않고 **컴파일 가능 여부만 확인** (거의 즉시 끝남)
  - ⚠️ dry-run 통과 ≠ 실제 컴파일 성공 보장 → **반드시 실제로 컴파일해서 확인**
  - 포럼에도 "설명과 다르게 동작", "성능 안 나옴", "fallback 발생" 같은 버그 리포트가 있음 → 컴파일러가 완벽하지 않음

### 6-8. 한계 & 커스텀 연산
- **CUDA 미지원**, 퓨리오사가 제공하는 커널로 만든 모델이 아니면 잘 안 돌아감 → 커스터마이징 어려움
- 해결책: **TCL (Tensor Contraction Language)** — 파이썬 기반으로 커스텀 연산 정의
  - 함수에 **데코레이터**를 붙여 입력을 지정하고, 실제 연산은 별도의 `tensor operation` 데코레이터 함수로 분리하는 것을 권장 (중복 연산 제거 최적화에 유리)
- 더 저수준 방식: 디바이스·HBM 텐서·클러스터·슬라이스까지 직접 지정 가능 (단, 1 더하기에도 fetch/collect/buffer 등 코드가 길어짐) → 병목 지점만 직접 최적화할 때 사용

### 6-9. ⭐ KV 캐시 문제 (교수님 과제)
> "KV 캐시를 너무 많이 잡아먹어서 **48GB에서 8B 모델밖에 못 쓴다.** 20B급이 돌아가는 사례가 있다는 건 KV 캐시를 줄였다는 얘기. **다음 주부터 한 달간 KV 캐시 줄이는 걸 연구**해봐라."

- 내일부터 팀당 **NPU 2장을 붙여서** 사용 → 컴파일 옵션(PE 수 등)이 실제로 메모리를 얼마나 잡는지 확인해볼 것
- KV 캐시는 서빙 단계 기능이라 `furiosa-llm`(별도 실행 환경)에서 구현되어 있음 → 공식 안내 문서 쪽을 참고

**[보충] KV 캐시 메모리 계산해보기**
```python
def kv_cache_gb(layers, kv_heads, head_dim, seq_len, batch, bytes_per=2):
    # K와 V 두 개(×2), bf16이면 2바이트
    return 2 * layers * kv_heads * head_dim * seq_len * batch * bytes_per / 1024**3

# Llama 3.1 8B: 32 layers, KV heads 8 (GQA), head_dim 128
print(kv_cache_gb(32, 8, 128, seq_len=32_768, batch=1))   # 약 4 GB
print(kv_cache_gb(32, 8, 128, seq_len=32_768, batch=8))   # 약 32 GB
# 가중치(bf16) 약 16GB + KV 캐시 → 48GB가 금방 찬다
```
KV 캐시를 줄이는 대표적인 방향 (연구 시작점):
- `max_model_len`(최대 컨텍스트 길이)·배치 크기 줄이기
- **KV 캐시 양자화** (FP8/INT8)
- **GQA/MQA** 구조 모델 선택 (KV head 수가 적음)
- **PagedAttention** 같은 블록 단위 메모리 관리
- 텐서 병렬(칩 2장)로 가중치를 나눠 KV 캐시 공간 확보

## ✅ 오늘의 핵심 요약
1. **CoT** = 풀이를 쓰게 하면 정답률 ↑ (단, 큰 모델·환각 한계)
2. **ReAct** = Thought→Action→Observation 루프로 외부 정보 확인 → 환각 ↓, 현재 에이전트의 기본 구조
3. **Reflexion** = 실패를 언어로 반성해 메모리에 저장하는 "말로 하는 강화학습", 평가자 품질이 생명
4. 세 방식은 경쟁이 아닌 **상호 보완** → 문제 유형에 맞게 선택
5. **NPU**: W·B는 레지스터에 고정, X만 흘려보냄 / 컴파일 모드·더블 버퍼링으로 속도 확보 / **KV 캐시 축소가 다음 과제**
6. 발표·메일은 **면접/정부과제 최종 제출이라고 생각하고** 디테일하게
