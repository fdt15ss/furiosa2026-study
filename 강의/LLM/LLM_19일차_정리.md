> 녹취(STT) 기반 정리입니다. 인식 오류가 많아 코드·변수명·수치는 문맥으로 복원한 **재구성 예시**이며, 실제 수업 파일과 다를 수 있습니다.

## 오늘의 핵심 요약

| 주제 | 한 줄 요약 |
|---|---|
| 동시 요청(스레드) 실험 | 워커(스레드) 수 1·2·4·8로 LLM 호출을 병렬 처리하며 시간·토큰·TPS 측정 |
| Continuous Batching | NPU 서버가 자동으로 요청을 묶어 처리 — 스레드 개념과 비슷하지만 사용자가 제어 불가 |
| 파이썬 기초 | `map()`, `lambda`, 삼항연산자, `enumerate(start=1)`, 패키지(`import`) |
| KV 캐시 / Prefix 캐시 | KV 캐시는 **낮을수록**, Prefix 캐시 적중률은 **높을수록** 좋다 |
| 서버 메트릭 수집 | `urllib.request`로 `/metrics` 텍스트를 가져와 파싱하는 `get_cache_metrics()` 함수 |

## 1. 스레드 동시 요청 실험 (워커 1 / 2 / 4 / 8)

### 1-1. 목적
- `ask`(= `run_once`) 함수는 LLM을 한 번 호출하는 함수.
- 프롬프트 8개를 **워커 1개, 2개, 4개, 8개**로 나눠 돌렸을 때 전체 처리 시간이 어떻게 달라지는지 비교.
- 워커 = 동시에 일하는 스레드 수. 워커가 2개면 2개씩 동시에 처리한다.

### 1-2. 측정 항목
- **경과 시간**: `time.perf_counter()`로 시작/끝 시점을 찍어 차이를 계산
- **토큰량**: `run_once`의 반환값(dict)에 `input_tokens`, `output_tokens`가 들어 있음
  - 결과가 여러 개(리스트)이므로 `for r in results:`로 돌면서 `output_tokens`를 합산 → `total_tokens`
- **TPS**: `total_tokens / 경과시간`

### 1-3. 재구성 예시 코드

```python
import time
from concurrent.futures import ThreadPoolExecutor

def bench(prompts, workers):
    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=workers) as ex:
        results = list(ex.map(lambda p: run_once(p, 100), prompts))
    elapsed = time.perf_counter() - start

    total_tokens = 0
    for r in results:
        total_tokens += r["output_tokens"]

    return elapsed, total_tokens, total_tokens / elapsed

for w in [1, 2, 4, 8]:
    print(w, bench(prompts, w))
```

### 1-4. 헷갈렸던 포인트: 결과 개수는 왜 항상 8개?
- `results`에는 **프롬프트 개수(8개)** 만큼 결과가 들어간다. 워커 수가 결과 개수를 바꾸지 않는다.
- 워커는 "한 번에 몇 개를 동시에 처리하느냐"일 뿐이다.
  - 워커 1 → 8번을 순서대로 / 워커 2 → 2개씩 동시에 / 워커 8 → 8개 한꺼번에
- 작업이 먼저 끝난 워커가 생기면 **대기 중인 다음 작업이 바로 투입**된다(작업 풀 방식).
- 결과: **워커가 늘수록 전체 시간은 줄고**, 총 토큰량은 동일 → TPS는 올라간다.

### 1-5. ThreadPoolExecutor vs Continuous Batching

| 구분 | ThreadPoolExecutor | Continuous Batching |
|---|---|---|
| 실행 위치 | 클라이언트(CPU) 쪽 파이썬 코드 | NPU/서버(런타임) 내부 |
| 제어 | 워커 수를 내가 지정 | 사용자가 제어 불가, 서버가 알아서 |
| 개념 | 요청을 N개씩 나눠 병렬 처리 | 요청을 모아 동적으로 묶어(배치) 처리 |

- 둘은 **엄밀히는 다른 것**이지만, "N빵 쳐서 동시에 병렬 처리한다"는 감각으로 이해하면 충분.
- 이 용어는 NPU뿐 아니라 LLM 서빙 업계에서 널리 쓰이므로 **용어 정도는 알아둘 것**.

## 2. 파이썬 기초 복습

### 2-1. `map()` 함수
- 문법: `map(함수, 리스트)` — 리스트의 값을 하나씩 함수에 넣어 결과를 만든다.
- **반환값은 바로 리스트가 아니라 `map object`(이터레이터)**.
  - 이터레이터를 보면 떠올릴 것: `for`문, `next()`
- 결과를 보려면
  - `list(map(...))`로 감싸거나
  - `for x in map(...):`로 순회

```python
def multiply(x):
    return x * 10

result = map(multiply, [1, 2, 3, 4])
print(result)         # <map object ...>
print(list(result))   # [10, 20, 30, 40]
```

### 2-2. `lambda` (익명 함수)
- `def`로 이름 붙여 정의하기 귀찮을 때 쓰는 **한 줄짜리 이름 없는 함수**.
- 형태: `lambda 매개변수: 반환식`  (콜론 앞 = 매개변수, 뒤 = return 값)

```python
# def 버전
def multiply(x):
    return x * 2

# lambda 버전
multiply = lambda x: x * 2
print(multiply(10))   # 20

# 매개변수가 2개
add = lambda x, y: x + y
print(add(1, 2))      # 3
print(add(3, 4))      # 7
```

#### 람다를 쓰는 이유 / 판단 기준
- 함수를 **인자로 넘겨야 하는 자리**(`map` 등)에서 별도 `def` 없이 바로 쓸 수 있다.
- 남이 짠 코드를 **읽을 줄 알아야** 한다 (직접 안 써도 읽기는 필수).
- 성능 차이는 사실상 없음(빠르다는 말도 있으나 체감 수준 아님).
- 람다는 "값이 들어갈 자리"에 쓸 수 있는 표현식이다 (`if`문은 문장이라 인자 자리에 못 넣지만, 삼항연산자는 값이라 가능한 것과 같은 원리).
- **반환식이 길어지면 `def`가 낫다.** 가독성이 우선.

#### 수업에서 `run_once`에 람다를 쓴 부분
```python
# ask 함수를 지우고, 람다로 대체
results = list(map(lambda p: run_once(p, 50), prompts))
```
- `map`이 `prompts`의 값을 하나씩 `p`에 넣고 → `run_once(p, 50)`이 실행 → 반환값이 모여 리스트가 된다.
- 프롬프트를 200개로 늘려도 동일하게 동작, TPS·지연시간도 정상 출력.

### 2-3. map + lambda + 삼항연산자 (합격/불합격 예제)

```python
scores = [85, 45, 70, 30, 90]
result = list(map(lambda x: "합격" if x >= 60 else "불합격", scores))
print(result)  # ['합격', '불합격', '합격', '불합격', '합격']
```
- 해석 순서: ① `map` → ② `lambda` 매개변수 `x` → ③ 조건식 참이면 앞값, 거짓이면 뒷값 → ④ 이터레이터를 `list()`로 변환.

### 2-4. `enumerate(..., start=1)`
- `for i, prompt in enumerate(prompts):` → `i`는 0부터 시작
- `enumerate(prompts, 1)`(= `start=1`)이면 **1부터 번호**를 붙일 수 있다 → 출력 시 "실험 1, 2, 3".
- `enumerate`가 보이면 이터레이터(+인덱스)라고 바로 떠올리기.

### 2-5. 문자열 곱하기로 긴 프롬프트 만들기
```python
base = "NPU란 무엇인가?"
desc = "NPU는 인공지능 연산을 가속하는 프로세서입니다. "
prompts = [
    base,
    base + desc * 100,   # 문자열 * 100 → 100번 반복
    base + desc * 300,
]
```
- 입력 토큰 길이를 인위적으로 늘리는 테스트용 방법.

### 2-6. 패키지/모듈 개념
- `파이썬_PKG` 폴더를 만들어 파일별로 정리.
- 자주 쓰는 함수(`run_once`, `get_cache_metrics`)를 공용 모듈 파일에 모아두고 `from 모듈 import 함수`로 불러 쓴다. (수업에서 "킹케라스"라고 부른 파일 — 녹취상 정확한 이름 불명확)
- 함수는 **재사용이 목적** → 출력(`print`)만 하지 말고 **`return`으로 값을 돌려줘야** 다른 파일에서 활용 가능.

## 3. KV 캐시와 Prefix 캐시

### 3-1. 개념 비교

| 항목 | KV 캐시 | Prefix 캐시 |
|---|---|---|
| 의미 | 모델이 추론하며 쓰는 **메모리 공간 사용량** | 프롬프트 **앞부분 중복 구간을 재활용**한 비율 |
| 지표 | `kv_cache_usage` (사용률 %) | `hit rate` (적중률 %) |
| 좋은 방향 | **낮을수록** 여유 (꽉 차면 위험) | **높을수록** 좋음 (재활용 ↑ → 캐시 소모 ↓) |
| 비고 | 90% 이상이면 주의 | 예) 84.5%면 좋은 값 |

- 두 개념은 **완전히 별개**이며 합쳐서 계산하는 것이 아님.
- 메모리 감각: 8B 모델을 양자화하면 약 8GB, 48GB 카드라면 나머지 약 40GB가 KV 캐시 공간으로 쓰인다.
- KV 캐시가 가득 차면 어떻게 되는지는 강사도 직접 끝까지 채워본 적 없다고 함 (미확인).
- 입력 프롬프트가 길수록 KV 캐시 사용률이 올라간다. (실습 중 1.7% → 약 10.3%로 증가)

### 3-2. 수동 확인 → 코드로 자동화
- 처음엔 서버 메트릭 화면을 열어 **Enter를 칠 때마다 갱신되는 값**을 눈으로 확인 (번거로움).
- 그래서 메트릭을 읽어오는 함수를 만들어 재사용.

## 4. 서버 메트릭 수집 함수 `get_cache_metrics()`

### 4-1. 동작 원리
1. 서버의 메트릭 주소(`127.0.0.1:포트/metrics`)를 `urllib.request.urlopen`으로 요청
2. 응답 텍스트를 줄 단위로 `split("\n")`
3. `#`으로 시작하는 줄은 **주석 → 건너뜀(`continue`)**
4. 나머지 줄에서 **이름(키)** 으로 필요한 항목을 찾고, **마지막 값**을 `float`로 변환해 누적
5. 적중률 = `hits / queries * 100`
6. **딕셔너리로 `return`** (queries, hits, hit_rate, kv_usage)

### 4-2. 재구성 예시 코드 (지표 이름은 예시)

```python
import urllib.request

def get_cache_metrics(url="http://127.0.0.1:포트/metrics"):
    queries = hits = kv_usage = 0.0
    with urllib.request.urlopen(url) as resp:
        text = resp.read().decode()

    for line in text.split("\n"):
        if line.startswith("#"):
            continue
        if "prefix_cache_queries" in line:
            queries += float(line.split()[-1])
        elif "prefix_cache_hits" in line:
            hits += float(line.split()[-1])
        elif "kv_cache_usage" in line:
            kv_usage = float(line.split()[-1]) * 100

    hit_rate = hits / queries * 100 if queries else 0
    return {"queries": queries, "hits": hits,
            "hit_rate": hit_rate, "kv_usage": kv_usage}
```

### 4-3. 디버깅 포인트
- 적중 횟수(hits)가 계속 **0**으로만 나오는 문제 → 원인은 **hits를 불러오는 부분의 오타**(문자열 키 이름 불일치).
- 문자열 안에 들어 있는 오타는 에디터가 잡아주지 않아 찾기 어렵다 → **따옴표 안 이름은 특히 주의**.
- 출력 포맷: `:.0f`(소수 0자리), `:.2f`(소수 둘째 자리).
- 함수가 완성되면 구현 세부는 몰라도 되고, **가져다 쓰면 된다**(알고리즘은 심심할 때 복습).

### 4-4. 실험 구성 및 결과
- 프롬프트 3개(짧은 것 → 100배 → 300배 길이), 출력 토큰은 **300으로 고정**(`max_tokens`).
- 각 실험마다 출력하는 항목:
  - 입력 토큰(`input_tokens`) — 프롬프트가 길수록 **증가**
  - 출력 토큰(`output_tokens`) — **고정(300)**
  - 응답 시간(`elapsed`, 소수 둘째 자리 반올림)
  - Prefix 조회 수 / 적중 수 / 적중률 / KV 캐시 사용률
- 결과 경향: Prefix 적중률 **약 62~66%**, KV 사용률 **약 13%** 수준에서 입력이 길수록 조금씩 상승 → 정상 범위.
- 활용: 코드를 짠 뒤 **KV 캐시 사용률이 90% 이상이면 위험 신호**로 보고 조심.

## 5. 머신러닝 상식 — 경진대회 재현성 (질의응답 내용)

- 학생 질문: 이전 대회 제출물(가중치·코드를 일부 분실)을 라벨로 삼아 다시 학습시켜 비슷한 점수를 재현해도 되는가?
- 강사 답변 요지
  - **랜덤 시드를 고정하지 않으면** 가중치 초기화·데이터 분할·배치 순서가 매번 달라져 **같은 코드여도 같은 결과가 안 나온다.** (재현이 안 되는 건 당연)
  - 자신이 만든 **논리 흐름(전처리 → 튜닝 과정)** 을 그대로 따라가 비슷한 성능을 내는 것은 괜찮다.
  - 하지만 제출물(정답에 가까운 예측)을 라벨로 과적합 학습시켜 등수를 맞추는 방식은 **정상적인 모델링이 아니다.**
  - 대회의 본질은 순위 숫자가 아니라 **기업의 문제를 해결하는 과정**. 면접에서도 "어떻게 올렸는지"를 묻는다.
  - 랜덤 서치 + XGBoost/LightGBM을 컴퓨팅 파워로 돌려 점수만 올리는 방식은 의미가 적다.
- 실천: **시드 고정 + 전처리/튜닝 과정 기록**을 습관화 (재현 가능성 확보).

## 6. 공지 / 기타

### 취업·면접
- 면접은 **많이 볼수록 좋다** (경험 삼아). 면접 일정이 발표/수업보다 우선.
- 면접 확인서(또는 명함)를 받아오면 출결 처리 가능 — 필요 서류는 매니저 확인.
- 면접 형식: 4:1 → 임원 포함 5:1로 변경된 곳도 있음.
- 이력서 첨삭: 11월 말~12월 초 진행 예정 (AI로 쓴 이력서는 티가 난다).
- 12월 초부터 정장 착용 목표. 12월 또는 이달 말쯤 회사 리스트 공유 예정.
- **금요일 11시**: 의료 AI(병원 AI센터 근무) 졸업생 특강 — 의료/비전/LLM 관련 질문 준비. (AI 분야에서 수익성은 금융 > 의료 순이라는 언급)

### 논문 스터디·발표
- 발표자는 랜덤 지정, **리젝(탈락)되면 다음 발표에서 해당 논문 발표 대상에서 제외**되는 식의 규칙.
- 발표 시작 멘트 예: "안녕하십니까, ○○ 논문 발표를 맡은 ○○팀 팀장 ○○○입니다."
- 긴장이 심하면 발표 1시간 전에 대비(우황청심원 등). 발표 한 번이라도 더 하는 게 이득.
- 이번 주 말부터 리액트 수업 진입 예정.

- [ ] 함수에서 `print` 대신 `return`을 써야 재사용 가능한 이유를 안다
- [ ] 재현성을 위해 랜덤 시드를 고정해야 하는 이유를 안다

## 간단 퀴즈

1. `map(lambda x: x*2, [1,2,3])`을 그냥 `print`하면 무엇이 출력될까? → `map object` (이터레이터), `list()`로 감싸야 `[2,4,6]`
2. 워커 수 8, 프롬프트 8개일 때 `results`의 길이는? → 8 (워커 수와 무관, 프롬프트 개수)
3. Prefix 캐시 적중률이 높으면 좋은 이유는? → 중복 구간을 재활용해 계산·캐시 소모를 줄이기 때문
