## 1. 모델 크기와 메모리 (딥러닝 추론 기초)

### 1-1. 파라미터 수 ↔ 메모리 용량 대략 환산

- `B` = **Billion(10억)**. 8B 모델 = 80억 파라미터.
- 정확하진 않지만 **"8B ≈ 8GB"** 로 대충 환산하면 된다 (FP8 기준 파라미터 1개 ≈ 1바이트).
- 30B 모델이면 약 30GB를 **GPU/NPU 메모리**에 올려야 한다.
- 실습 장비는 NPU 1장 = **48GB** 이므로 이론상 8B는 문제없이 올라간다.

### 1-2. 그런데 48GB를 다 못 쓰는 이유: KV 캐시

- 모델 가중치(8GB)를 올리고 나면 **남은 메모리를 거의 전부 KV 캐시에 할당**한다.
- KV 캐시 = Attention에서 쓰는 **Key / Value 값을 저장해 두는 메모리**.
- 이 할당 방식은 제조사(퓨리오사)가 설계한 것이라 사용자가 건드릴 수 없다.
- 실제로 8B 모델을 띄우면 `furiosa-smi status` 에서 메모리 사용률이 **약 96%** (45~46GB) 까지 올라간다.
- 장점: 캐시를 많이 들고 있어서 **두 번째, 세 번째 요청부터 응답이 더 빠르다**. (추론 전용 설계)
- 단점: 학습용이라면 바로 비워서 재사용해야 하므로 이런 방식과는 맞지 않는다.

### 1-3. 실습에서 확인한 사용량

| 모델 | 메모리 사용량(대략) |
|---|---|
| 8B 모델 | 45~46GB (KV 캐시 포함) |
| GPT-OSS 20B | 약 35~38GB (컴파일/양자화가 잘 되어 있음) |
| 4B 모델 | 약 절반 수준 |

### 1-4. 더 큰 모델을 쓰려면

- 장 수를 늘린다 (16GB급이면 2장, 30B급이면 4장 서버 등).
- 프로젝트 때는 **NPU 2장을 병렬로 묶어서** 쓰게 될 예정 → 최소 16B급까지 가능하다고 안내.
- 장비 가격 참고(수업 중 언급): RNGD 4장 서버 약 1.5억 원. 30B급 모델을 로컬에 두고 쓰면 월 구독료 대비 가치를 낼 수 있다는 설명.

## 2. 컴파일 / FXB / 양자화

### 2-1. FXB (퓨리오사 컴파일 결과물)

- 퓨리오사 NPU는 **퓨리오사 전용 컴파일이 된 모델(FXB 파일)** 만 돌아간다. (약어는 Furiosa eXtended Binary 계열로 추정, 확인 필요)
- 그래서 **작은 모델이라도 FXB가 없으면 실행이 안 된다.**
- 실제로 Qwen3 0.8B 같은 작은 모델이 에러가 난 것도 "FXB 파일이 없다"는 메시지 때문이었다.
- 퓨리오사 쪽 엔지니어가 컴파일해서 Hugging Face(`furiosa-ai/...`)에 올려둔 모델만 쓸 수 있다.
- 직접 컴파일할 수도 있지만 **시간이 매우 오래 걸린다** (최소 2시간 이상 예상).
- 로컬에 컴파일해서 받아도, 캐시로 당겨 쓰는 것과 **성능 차이가 크지 않다**는 설명.

### 2-2. 학습/튜닝은 NPU 영역이 아님

- NPU는 **추론 전용**: 레이어 추가, 파라미터 변경, 하이퍼파라미터 튜닝, 전이학습은 **GPU 영역**.
- 거대 언어 모델은 직접 건드려서 성능이 좋아지는 경우가 거의 없다.
- 랭체인/랭그래프/에이전트는 전부 **추론 결과를 활용하는 개념**.

### 2-3. 양자화 (내일 테스트 예정)

- 가중치 정밀도를 낮춰서 용량을 줄이는 작업. 예) `FP16 → FP8`, `FP8 → INT4`
- 용량이 크게 줄어 큰 모델도 올릴 수 있다.
- 부작용: **답변 품질/성능이 떨어진다.**
- 고민 포인트: *16B를 양자화해서 올리는 것 vs 8B를 제대로 돌리는 것* 중 무엇이 나은지.
- 참고: PyTorch의 양자화 API는 "진짜 양자화"가 아니라 **양자화를 흉내낸 것**이다. (양자컴퓨팅의 양자와는 전혀 다른 개념)

## 3. NPU vs GPU

| 항목 | GPU | NPU (퓨리오사) |
|---|---|---|
| 성능 | 더 높음 | 추론에 특화 |
| 학습 | 가능 | 불가 |
| 전력 | 많이 소모 | 약 절반 수준이라고 소개 |
| 용도 | 학습 + 추론 | **추론/서비스** |
| 장비 가격 | 비슷하거나 약간 비쌈 | 비슷 |

- 챗GPT 같은 서비스는 **학습보다 추론(서비스)** 비중이 압도적으로 크다. 추론만 하는데 비싼 GPU와 전력을 쓸 이유가 없다는 논리.
- 학습도 같이 하는 회사라면 GPU를 구성해야 한다.
- 시장이 **학습 시장 / 추론 시장**으로 나뉘며, 에이전트 개발은 추론 시장에 속한다.
- 국내는 대부분 "기승전 API" 라서 NPU로 API를 따라잡긴 어렵지만, 정부 지원 사업으로 NPU 서버를 도입한 회사가 많아 현장에서 만날 가능성은 있다.

### CPU / GPU 코어 비유

- CPU 코어: 강호동 10명이 물동이를 나르는 것 (코어 수는 적지만 강함)
- GPU CUDA 코어: 유치원생 2만 명이 작은 물통을 나르는 것 (병렬로 한 번에 많이)
- NPU의 "코어"는 CUDA 코어와 달리 **수백~수천 개를 묶은 코어 블록** 개념. (정확한 수치는 비공개, 8개 블록으로 설명)

## 4. Linux / WSL / SSH 명령어 정리

### 4-1. WSL

```powershell
wsl -l -v                # 설치된 배포판 + 버전 목록
wsl -l -o                # 설치 가능한 배포판 목록
wsl --install -d Ubuntu-24.04 --name <이름>   # 배포판 + 이름 지정 설치
wsl -d <이름>            # 해당 배포판으로 접속
```

- 같은 버전의 우분투도 **`--name`을 다르게 주면 여러 개 설치 가능**.
- `-d` = distribution, `-n` = name 의미.
- 대소문자: 윈도우 CMD는 구분을 안 하는 경우가 있지만, 리눅스는 구분하므로 **항상 대소문자를 맞춰 쓰는 습관**.
- **PyTorch/TensorFlow의 GPU 사용은 최신 버전(TF 2.11~ 이후)부터 Linux에서만 지원** → 앞으로 GPU 작업은 WSL에서 진행할 예정. (정확한 버전은 확인 필요)
- WSL에서 `nvidia-smi` 가 바로 동작한다 → **윈도우에 설치한 CUDA 드라이버를 공유**하므로 WSL에 따로 설치할 필요가 없다.

### 4-2. SSH 키 세팅

```bash
mkdir .ssh               # 점(.)이 붙은 폴더는 보통 숨김/중요 폴더
ls -a                    # 숨김 파일 포함 전체 목록
cd .ssh
chmod 600 id_rsa         # 키 파일 권한 (소유자만 읽기/쓰기)
```

```powershell
# 접속 (포트는 개인별로 다름)
ssh -i <키파일경로>/id_rsa -p <포트번호> <계정>@<호스트>
```

- `-i` : 사용할 키 파일(identity)
- `-p` : 포트 번호 (22번이 아니라 퓨리오사 측이 매핑해 준 포트)
- 포트는 2개: **SSH용 1개 + 서비스(8000번 등)용 1개**
- 첫 접속 시 fingerprint 질문은 `yes`.
- **키 파일은 노출 금지.** PC방 같은 곳에서 쓰지 말 것.
- 비밀번호/키 설정이 어긋나면 접속이 안 되므로 **오타, 경로, 버전, shape** 가 문제 확인 1순위.
- Windows 쪽 `C:\Users\<계정>\.ssh\config` 에 호스트를 등록해 두면 VS Code Remote-SSH에서 바로 뜬다.
- VS Code 연결: `Ctrl+Shift+P` → `Remote-SSH: Connect to Host`.

### 4-3. 기타 명령

```bash
sudo apt update          # 패키지 목록 갱신 (root 계정이면 sudo 없이도 가능)
cd ..                    # 상위 폴더
source ~/.bashrc         # 설정(conda PATH 등) 다시 적용
```

- `sudo` = 슈퍼유저(root, 최고 관리자) 권한으로 실행
- 리눅스 실무에서는 명령을 일일이 타이핑하기보다 **미리 작성된 배치/스크립트를 복사-붙여넣기**하는 경우가 많다. 그래도 명령어의 뜻은 찾아서 알아두는 것이 좋다. (특히 DB, 쿠버네티스 작업은 오타 하나로 사고가 난다)

## 6. Hugging Face 인증 → 모델 서빙 → OpenAI 클라이언트 호출

### 6-1. Hugging Face 토큰 발급

1. Hugging Face 로그인 → **Settings → Access Tokens**
2. `Create new token` → 토큰 타입 **Read** → 이름은 자유(예: `furiosa-npu`)
3. 생성된 토큰(`hf_...`) 복사. **다시 볼 수 없으니 바로 저장**하고 외부에 공유하지 않는다.
4. 토큰은 무료이므로 여러 개 만들어도 된다.

### 6-2. 서버 터미널에서 설치 및 로그인

```bash
pip install huggingface_hub    # 최신 버전 권장
hf --help
hf auth login                  # 토큰 붙여넣기 (마우스 우클릭, 입력 시 화면에 안 보임)
hf auth whoami                 # 현재 로그인 계정 확인
hf cache ls                    # 캐시로 받은 모델 목록, 용량, 받은 날짜
```

- 이번 실습에서 `whoami` 결과가 다른 사람 계정으로 나온 이유: **같은 서버 캐시 경로를 공유**하고 있어서 누가 로그인하면 다른 사람 인증이 덮어써지거나 풀리는 현상. (퓨리오사 측에 문의 예정)
- 모델 다운로드(캐시)와 서빙 자체는 큰 문제 없이 동작했다.

### 6-3. 모델 서빙

```bash
furiosa-llm serve furiosa-ai/<모델명>
```

- 모델을 메모리에 올려놓고 **대기(Ready) 상태**로 만든다. (웹서버를 켜놓는 것과 같은 개념)
- 이 터미널은 서버가 점유하므로 **그대로 두고**, 다른 터미널을 추가로 열어 작업한다.
- 종료는 `Ctrl+C` → 메모리가 0으로 반환됨.
- 모델은 **한 번에 하나만** 올릴 수 있다. 2개를 동시에 돌리려면 장비가 더 필요하다.
- 공식 문서: `developer.furiosa.ai` → 지원 모델 / 빠른 시작 문서 참고. **Stable(예: 2026.x.0 안정 버전) 기준**으로 진행해야 안 깨진다.

### 6-4. 모니터링용 터미널

```bash
watch -n 1 furiosa-smi status
```

- 1초 간격으로 갱신되는 모니터링. 모델 로딩/요청 시 메모리·코어 사용률이 움직이는 걸 볼 수 있다.
- `Ctrl+C` 로 빠져나옴.
- GPU 쪽은 `nvidia-smi` 가 같은 역할.

### 6-5. OpenAI 클라이언트로 로컬 서버 호출 (핵심 코드)

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8000/v1",   # 로컬 서빙 주소
    api_key="EMPTY",                       # 로컬 서버는 키 불필요 (임의 값)
)

response = client.chat.completions.create(
    model="furiosa-ai/<모델명>",            # 서빙한 모델명과 동일하게
    messages=[
        {"role": "user", "content": "안녕하세요. 자기소개를 해주세요."}
    ],
    max_tokens=3000,
)

print(response.choices[0].message.content)
```

- 원래는 `requests` 로 HTTP 요청-응답을 직접 처리해야 하는데, **OpenAI SDK가 대신 처리**해 주므로 코드가 간결해진다.
- `127.0.0.1` = `localhost` = 자기 자신. `0.0.0.0` 은 외부에서도 접근 가능, `127.0.0.1` 은 내부에서만 접근.
- 모델을 바꿀 때 바꿔야 하는 곳은 **`model=` 부분 하나뿐**.
- 응답 구조는 `list / dict` 로 되어 있으므로 `choices[0].message.content` 처럼 점/인덱스로 찾아 들어간다. 모델/버전마다 다르므로 **처음 쓰는 모델은 `print(response)` 로 구조를 먼저 확인**.
- 서버를 꺼놓은 상태에서 코드를 실행하면 연결 에러.
- 하이브리드 구성도 가능: **빠르게 돌려야 하거나 비용이 큰 작업은 로컬 모델**, **성능이 더 필요한 작업은 OpenAI/Claude API** 를 섞어 쓸 수 있다. (리눅스 서버도 결국 일반 PC이므로)

### 6-6. `max_tokens` 관련

- `max_tokens` 가 너무 작으면(예: 300) 답변이 **도중에 끊겨서** 이상하게 보인다.
- 3000 정도로 늘리니 한국어 답변이 정상 출력되었다.
- 로컬 모델은 토큰당 비용이 없으므로 크게 잡아도 부담이 없다.

## 9. 머신러닝: K-Fold & 교차검증

### 9-1. 왜 필요한가

- 기존 방식: `train_test_split` 으로 **테스트 데이터를 아예 학습에서 배제** → 평가만 하고 버려지는 데이터.
- 귀하게 모은 데이터가 아깝고, 특히 **데이터가 적을 때 손실이 크다.**
- K-Fold: 전체 데이터를 **K등분**하고, 매번 1조각을 테스트로 쓰고 나머지로 학습 → **K번 반복**. 결국 모든 데이터가 한 번씩 테스트에 쓰인다.
- 5-Fold이면 한 번의 학습에는 **80%** 데이터가 쓰이고, 전체 데이터 입장에서는 4번 학습에 참여한다.

### 9-2. 오해하기 쉬운 포인트 (질문 정리)

| 질문 | 답 |
|---|---|
| 5개 모델이 가중치를 공유하나? | **아니오.** 매번 새로 학습하는 **완전히 별개의 훈련**. 그래서 엄밀한 의미의 과적합 문제도 아니고 앙상블도 아니다. |
| 같은 모델을 5개 복사해서 쓰나? | 같은 모델 **설정**으로 **5번 처음부터** 학습한다. |
| 결과는 어떻게 쓰나? | 5개 점수의 **평균(mean)** 으로 모델/설정을 평가한다. |
| 최종 모델은? | 점수가 괜찮은 설정을 확인한 뒤 **전체 데이터로 다시 학습**하거나, 5개 모델의 예측을 합쳐(`predict` 후 평균) 사용할 수도 있다. |
| 점수가 들쭉날쭉하면? | 데이터가 적거나 분포 편향이 있다는 신호 → 데이터 보강/증폭 고려. 점수가 **고르면** 안정적인 모델. |
| `random_state` 로 분할만 바꿔도 되지 않나? | 비슷한 효과는 있지만, K-Fold는 **겹치지 않게 보장**해 준다. |
| K는 몇으로? | 보통 **5, 3, 10**. 데이터가 매우 크면 K를 키워도 됨. 학습 시간은 대략 K배. |
| 시계열 데이터는? | 순서가 중요하므로 일반 K-Fold를 그대로 쓰면 안 됨 (3차원으로 만든 뒤 별도 분할 방식 필요). |

> 추후 확인: "K-Fold로 합친 뒤 최종 평가는 어떻게 하나?" → 별도의 **순수 테스트 셋**을 남겨 두는 방식 등은 다음 시간에 다룬다고 함.

### 9-3. 위치: 데이터 분석 파이프라인에서

- **#1 데이터 전처리** 단계에 해당 (Train/Test Split을 대체하는 분할 방법).
- K-Fold와 **교차검증(Cross Validation)** 은 항상 짝으로 등장.

### 9-4. 코드 (분류 모델 예시)

```python
import numpy as np
from sklearn.model_selection import KFold, cross_val_score
from sklearn.tree import DecisionTreeClassifier

# 1) 데이터 준비
X, y = ...   # 이미 분리된 특성/타깃

# 2) K-Fold 정의 : 5등분, 섞기, 재현성을 위한 seed
kfold = KFold(n_splits=5, shuffle=True, random_state=42)

# 3) 모델 (머신러닝 모델은 기본값도 강력)
model = DecisionTreeClassifier()

# 4) 교차검증: fit까지 알아서 해줌 (훈련 + 평가)
scores = cross_val_score(model, X, y, cv=kfold)

# 5) 결과
print("fold별 점수:", scores)
print("평균:", round(np.mean(scores), 4))
```

- `cross_val_score(모델, X, y, cv=...)` : **fit을 따로 호출할 필요가 없다.**
- `cv=kfold` 대신 정수 `cv=5` 로 써도 동작한다.
- `shuffle=True` : 분할 전에 데이터를 섞는다.
- 변수명 `cv` 는 **Cross Validation** 의 약자 (이미지 CV 아님).

### 9-5. 평가 기준 (scoring 기본값)

| 모델 종류 | `score()` / `cross_val_score` 기본 기준 |
|---|---|
| 분류 | **정확도(Accuracy)** |
| 회귀 | **R²** (실제 데이터와 예측선의 설명력) |

- 회귀는 정답이 1/0으로 떨어지지 않으므로 정확도를 쓸 수 없고, MSE는 오차 크기라서 기본 점수는 **R²** 를 쓴다.
- 사이킷런, XGBoost 등 모든 모델에서 동일.

### 9-6. 실습 결과 해석

- 분류 예시에서 5개 점수가 `0.93, 0.91, 0.96, 0.93 ...` 정도로 나옴 → 평균 약 0.94.
- 일부 fold에서 `0.9` 와 `1.0` 처럼 편차가 크면 **데이터가 작아서** 생기는 현상으로 의심.
- 디시전트리와 랜덤포레스트를 바꿔 비교 → 랜덤포레스트가 더 좋은 성능, 단 시간이 더 걸림.
- 과제: **캘리포니아 주택 데이터(회귀)** 로 K-Fold 교차검증을 해 보고, 예전에 구한 최적 결과와 비교. (목표 R² 약 0.85 이상이라는 언급)
- 이 단계는 모든 모델 튜닝의 **가장 기본 바닥**이므로 반드시 복습.
