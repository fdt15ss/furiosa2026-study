## 1. 오전: 그리드 서치 → 랜덤 서치

### 1-1. 왜 랜덤 서치인가
- **그리드 서치(GridSearchCV)**: 후보 조합을 **전부** 돌린다. 가장 기본적이고 무식한 방법이지만 지금도 쓰인다.
  - 예) 파라미터 10 × 10 × 10 … 이면 1,000번, 여기에 CV 5를 곱하면 5,000번 → 비용이 너무 크다.
- **랜덤 서치(RandomizedSearchCV)**: 후보 조합 중 **일부만 무작위로 뽑아서** 돌린다.
  - 신기하게도 그리드 서치보다 성능이 **비슷하거나, 가끔은 더 좋게** 나오기도 한다.
  - (그리드 서치가 전체를 다 보니 이론상 더 좋아야 하지만, 평가 방식·랜덤 선택에 따라 역전될 때가 있음)
- 알고리즘은 같고 **차이는 단 하나**: 전체를 다 돌리냐 / 랜덤하게 뽑아서 돌리냐.

### 1-2. 코드 변경 (그리드 → 랜덤)
```python
# 변경 전
from sklearn.model_selection import GridSearchCV
model = GridSearchCV(xgb, param_grid=parameters, cv=kfold, verbose=1, n_jobs=-1)

# 변경 후
from sklearn.model_selection import RandomizedSearchCV
model = RandomizedSearchCV(xgb, param_distributions=parameters, cv=kfold,
                           n_iter=10, verbose=1, n_jobs=-1, random_state=333)
```
- 데이터, K-Fold, 파라미터 딕셔너리, 모델(XGBoost)은 **그대로** 사용 가능.
- import 이름과 클래스명만 `Grid` → `Randomized`로 바꾸면 된다.

### 1-3. 핵심 파라미터: `n_iter`, `random_state`, `refit`

| 파라미터 | 의미 |
|---|---|
| `n_iter` | 전체 후보 중 **몇 개를 뽑을지** (기본값 **10**) |
| `random_state` | **어떤 파라미터 조합을 뽑을지**를 정하는 난수 시드 (고정하면 재현 가능) |
| `refit` | 최적 파라미터로 **마지막에 한 번 더 전체 훈련**할지 (기본값 **True**) |
| `cv` | 교차검증 폴드 수 |

#### 몇 번 돌아가는가? (선생님이 "뻥친" 부분)
- 출력 예: `Fitting 5 folds for each of 10 candidates, totalling 50 fits`
- 그리드 서치 예: 42개 후보 × 5 fold = **210 fits**
- 랜덤 서치: `n_iter(10) × cv(5) = 50 fits` → **하지만 실제로는 +1회 (refit) = 51번**
- 설명 중 사용한 숫자 예시: 240번 돈다고 했지만 실제로는 **241번** (마지막 refit 1회 추가)
- `n_iter=1`이면 candidate 1개, `n_iter=3`이면 3개 → `n_iter` 값으로 후보 수를 직접 조절.

#### `refit`의 역할
- 탐색(CV)에서는 **train 데이터를 K-Fold로 쪼개서** 일부만 학습에 쓴다.
- 최적 파라미터를 찾은 뒤, 그 파라미터로 **train 전체를 다시 한 번 훈련**하는 것이 refit.
- `refit=False`로 두면 마지막 훈련을 안 하므로 `model.score()`, `model.predict()` 등에서 **에러**가 난다. (최종 모델이 없기 때문)
- 즉, `best_estimator_`, `predict`, `score`를 쓰려면 `refit=True`(기본값)여야 한다.
- 평가는 항상 따로 떼어둔 **test 데이터**로 한다. (train → K-Fold 탐색 / test → 최종 평가)

#### `random_state` 주의
- `RandomizedSearchCV`에는 `random_state`가 **있다** (조합을 랜덤으로 뽑으니까).
- `GridSearchCV`에는 `random_state`가 **없다** → 넣으면 `unexpected keyword argument 'random_state'` 에러. (전부 다 돌리니 랜덤이 필요 없음)
- `random_state`를 바꾸면 **뽑히는 조합이 달라져서 best_params_도 달라질 수 있다.**

### 1-4. 실습 과제
- 그리드 서치로 했던 `diabetes`, `digits` 두 데이터셋을 랜덤 서치로 바꿔서 실행.
- 단일 모델(튜닝 X)과 튜닝한 모델의 성능도 비교해 보기.
- `random_state`를 바꿔가며 최적 파라미터가 어떻게 변하는지 확인.

### 1-5. 이후 진도 예고 (오전 계획)
- 랜덤 서치 → **Halving → 베이지안 최적화 → 보팅 → 배깅 → 스태킹**

## 2. 오전: 케라스 모델의 하이퍼파라미터 튜닝 자동화

> 학생들이 원하던 "케라스 튜닝 자동화"를 랜덤 서치로 구현.

### 2-1. 튜닝 대상이 되는 것 / 안 되는 것
- **튜닝 대상(하이퍼파라미터)**: learning rate, optimizer, activation, dropout 비율, epochs, batch_size, 각 층의 node 수 등
- **고정하는 것**: `Sequential`/함수형 같은 모델 구조 자체, 층 개수(복잡해지므로 일단 고정)
- 수동 튜닝은 `for`문으로도 가능. (선생님이 본 사례: 대충 만든 모델에 `for`문 + 랜덤서치만 돌려서 대회에서 성능을 크게 올린 사람도 있음)

### 2-2. 모델을 "함수"로 만들기 (함수형 API)
하이퍼파라미터를 **인자(디폴트값 포함)** 로 받는 빌드 함수를 만든다.

```python
from tensorflow.keras.models import Model
from tensorflow.keras.layers import Input, Dense, Dropout

def build_model(drop=0.5, optimizer='adam', activation='relu',
                node1=128, node2=64, node3=32, node4=16, node5=8,
                lr=0.001):
    inputs = Input(shape=(10,), name='inputs')                 # diabetes: feature 10개
    x = Dense(node1, activation=activation, name='hidden1')(inputs)
    x = Dropout(drop)(x)
    x = Dense(node2, activation=activation, name='hidden2')(x)
    x = Dropout(drop)(x)
    x = Dense(node3, activation=activation, name='hidden3')(x)
    x = Dense(node4, activation=activation, name='hidden4')(x)
    x = Dense(node5, activation=activation, name='hidden5')(x)
    outputs = Dense(1, activation='linear', name='outputs')(x)  # 회귀 → linear

    model = Model(inputs=inputs, outputs=outputs)
    model.compile(optimizer=optimizer, loss='mse', metrics=['mae'])
    return model
```
- 함수를 호출할 때 `build_model(node1=33, activation='selu', drop=0.7)`처럼 **값을 바꿔서 모델을 생성**할 수 있다. → 이게 곧 튜닝.
- 중간 층 이름이 같아도 에러는 아니지만, **skip connection**처럼 연결이 복잡해지면 이름을 명시해야 한다.
- 시퀀셜은 이렇게 함수 안에서 하이퍼파라미터를 바꾸기 어려워서 **함수형 모델**이 편하다.
- 마지막 출력층: 회귀 문제이므로 `activation='linear'`.

### 2-3. 하이퍼파라미터 딕셔너리 만들기
```python
def create_hyperparameter():
    batchs     = [32, 16, 8, 64]
    optimizers = ['adam', 'rmsprop', 'adadelta']      # 녹취상 일부 불명확 → 예시
    dropouts   = [0.2, 0.3, 0.4, 0.5]
    activations = ['relu', 'elu', 'selu']             # 녹취상 일부 불명확 → 예시
    node1 = [128, 64, 32, 16]                         # 2의 배수 형태
    ...
    return {
        'batch_size': batchs,
        'optimizer': optimizers,
        'drop': dropouts,
        'activation': activations,
        'node1': node1,
        # node2 ~ node5, lr(learning rate) 도 같은 방식
    }

hyperparameters = create_hyperparameter()
print(hyperparameters)   # dict: {키: [후보 리스트]} → 그리드/랜덤서치에서 쓰던 형태와 동일
```
- 튜닝할 파라미터가 8개이고 각각 2가지만 있어도 2⁸ = 256 조합이 된다.
- 결과는 `{ 'batch_size': [...], 'optimizer': [...] ... }` 형태의 **딕셔너리** → 머신러닝 때 쓰던 `parameters`와 같은 구조.

> **💡 왜 node, batch_size를 2의 배수로?**
> 2진수 기반이라 개발자들이 관습적으로 2의 거듭제곱(2, 4, 8, 16, 32, 64…)을 많이 쓴다. 실제로 성능이 더 좋을 수도 있고, 사실 "있어 보이는" 이유도 있다. 신입이 batch_size를 31로 설정하면 선임이 "왜 31이야?"라고 물어보게 된다.

### 2-4. 케라스 모델을 랜덤 서치에 연결하기 (에러 해결 과정)

**에러 1: `estimator should be an estimator implementing 'fit' method`**
- 원인: `RandomizedSearchCV`에 **케라스(텐서플로) 모델/함수**를 그대로 넣었기 때문. 사이킷런은 텐서플로 모델을 인식하지 못한다.
  - (XGBoost는 원래 자체 API가 있지만 **사이킷런 형식으로 wrapper를 만들어 둔 것**이라 잘 돌아갔던 것.)
- 해결: 케라스 모델을 **사이킷런 형태로 감싸는(wrapping) 래퍼**를 사용.

```python
from scikeras.wrappers import KerasRegressor     # 분류는 KerasClassifier

keras_model = KerasRegressor(model=build_model, verbose=1)   # build_fn → model 로 인자명 변경
```

**에러 2: `hyperparameters` 이름 오타 / 함수 자체를 넣은 문제**
- `param_distributions`에는 함수가 아니라 **`create_hyperparameter()`의 반환값(딕셔너리)** 을 넣어야 한다.

### 2-5. 최종 랜덤 서치 구성

```python
from sklearn.model_selection import RandomizedSearchCV

model = RandomizedSearchCV(keras_model, hyperparameters,
                           cv=3, n_iter=10, random_state=333, verbose=1)
```
- `cv=3`으로 줄인 이유: 시간이 너무 오래 걸려서. (선생님도 CV3은 좀 약하다고 언급)
- 이전 머신러닝 실습의 `import time`, 시작/종료 시간 측정, 결과 출력 코드를 **그대로 재사용**.

### 2-6. fit에 콜백/검증 데이터 추가 (실제 케라스 훈련처럼)

랜덤 서치가 눈 깜짝할 사이에 끝난 건 **epochs가 빠져 있어서**였다. → `epochs`를 넣어야 진짜 훈련이 된다.

```python
from tensorflow.keras.callbacks import EarlyStopping, ReduceLROnPlateau

es = EarlyStopping(monitor='val_loss', mode='min', patience=10,
                   restore_best_weights=True, verbose=1)
rlr = ReduceLROnPlateau(monitor='val_loss', mode='auto', patience=8,
                        factor=0.8, verbose=1)      # 감소율 80%로 (반으로 안 줄임)

start = time.time()
model.fit(x_train, y_train,
          epochs=100,
          validation_split=0.1,          # 검증 데이터 10%
          callbacks=[es, rlr])
end = time.time()
```
- **EarlyStopping/ReduceLROnPlateau는 `val_loss`를 모니터링하므로 검증 데이터 정의가 필요**하다. (`validation_split` 없으면 loss 기준으로 바뀌는 등 동작이 애매해짐)
- 콜백은 `fit`의 `callbacks=[...]`에 넣는다.
- ModelCheckpoint(저장)도 가능하지만 이번엔 생략.
- 얼리스토핑이 걸려도 **전체가 끊기는 게 아니라 그 한 번(fold)의 훈련만 멈춘다.** 나머지 조합/fold는 계속 돈다.
- 총 훈련 횟수: `n_iter 10 × cv 3 = 30번` + refit 1번 = **31번**.
- 결과 확인: `best_score_`, `best_params_`, `best_estimator_` 등을 프린트해서 확인 (프린트는 줄바꿈해서 보기 좋게).

### 2-7. 트러블슈팅: `n_jobs=-1` → Out of Memory
- 증상: 실행 중 **OOM(Out of Memory) 에러**.
- 원인: `n_jobs=-1` → CPU **전 코어**를 병렬로 잡아버림. 케라스 훈련은 메모리를 많이 쓰므로 한계 초과. (GPU + CPU 동시 사용이 더 빠르진 않음)
- 해결: `n_jobs`를 **8개 정도로 제한**.
- **오늘의 핵심 교훈: `n_jobs=-1`을 함부로 쓰지 말자.**
- 시스템이 이상해지면 **커널/주피터를 재시작**해서 복구.

### 2-8. 메모

- **keras 튜닝의 한계/의의**: "튜닝의 끝은 순정"이라는 농담 — 디폴트값에는 이유가 있다. 자동 튜닝이 항상 큰 차이를 만드는 건 아니다.
- 튜닝은 케라스뿐 아니라 **PyTorch**에도 똑같이 적용 가능하다.

## 3. 오후 Q&A: 은닉층(Hidden Layer)은 알 수 있는가?

- 입력 데이터(예: 2×2×3)가 Flatten/Reshape으로 펼쳐지면, 그 이후 은닉층에서는 **"원래 어느 축/좌표의 정보였는지"를 사람도, 컴퓨터도 알 수 없다.** 컴퓨터는 **숫자(수치)만** 가지고 있다.
- 모델은 어떤 노드가 중요한지 "이해"하는 게 아니라, 결과(출력)와 정답을 비교해서 **경사하강법(Gradient Descent)으로 가중치를 갱신**하며 예측값을 정답에 맞춰갈 뿐이다.
- 고차원(예: 임베딩 벡터 1,000차원 이상)은 사람이 직접 계산·해석할 수 없고, 특정 은닉 노드가 왜 중요한지 밝혀내면 **노벨상급**이라는 농담이 나올 만큼 미해결 문제 → 그래서 이름이 **"히든(hidden)"**.
- 차원이 내려갈수록 손실되는 정보가 있지만, 그 부분을 모델이 어떻게 처리하는지도 설계자조차 정확히 모른다.
- 모델이 "이해한다"고 말하는 건 잘못된 생각 → 단지 **연산**하는 것.

## 4. 리눅스 / SSH 접속 복구 (실습 서버 환경)

> 서버 접속 키 초기화 문제 발생 → 해결 절차 (수업 중 팀별 실습)

### 상황
- 실습 서버는 **쿠버네티스 기반 가상 파드**. 물리 서버 1대에 파드가 4개씩 묶여 있어서, 같은 물리 서버에서 작업하던 학생들이 **동시에 문제**를 겪었음.
- 원인 추정: **캐시/용량이 꽉 차서** 접속 정보(키)가 초기화됨.

### 복구 절차 요약
1. 접속 정보(키)가 초기화되었으므로 **키를 다시 교체**해야 한다.
2. 키는 **두 군데**에 넣어야 한다: **WSL(리눅스)** 쪽과 **Windows** 쪽(`.ssh` 폴더, `config` 파일).
3. 키 파일 **권한 변경**이 필요하다.
   ```bash
   chmod 600 ~/.ssh/<키파일>
   ```
   - Windows PowerShell에서는 `chmod`가 아니라 **PowerShell용 권한 설정 명령**(icacls 등)으로 동일한 작업을 한다.
4. 접속 전에 `.ssh` 폴더에 **불필요한 다른 키 파일(RSA 외)은 정리**한다.
5. 접속 시 "Are you sure you want to continue connecting?"가 나오면 `yes`.
6. **파일이 있는 경로(홈 디렉토리 등)** 에서 작업해야 파일이 정상 적용된다. WSL 경로와 Windows 경로를 혼동하지 않도록 주의.
7. VS Code(Remote-SSH)에서도 `config`의 Host 설정이 있어야 접속 가능.

### 참고
- 회사에서도 **리눅스 서버 한 대를 여러 명이 나눠 쓰는** 환경이 많음 (중대형 서버, 도커 환경, 쿠버네티스 환경 등).
- 기본은 **SSH로 접속**한다는 것만 알아도 되고, 세팅 방법은 회사마다 달라서 메모장/문서로 알려주는 대로 **한 땀 한 땀 따라하면 된다.**
- 주말에 서버 문제 생기면 담당 강사에게 **메일**로 연락.

### 프로젝트
- **POC 프로젝트 1개(필수)** + **본인들이 하고 싶은 프로젝트 1개**.
- 기업 POC 주제가 본인 관심사와 맞으면 그것 하나만, 안 맞으면 2개 진행.

### 기타
- 자리 배치: 번호 추첨으로 자리 선택 (팀원끼리 상의 가능).
- 오후에는 매니저 면담(1인 30분, 약 3~4시간) → 그 시간에 **논문 스터디**.
- 컨디션/정신 상태가 이상하다 싶으면 **팀원·강사·매니저에게 꼭 이야기하기**.

## ✅ 오늘의 핵심 요약

1. **RandomizedSearchCV** = 후보 중 `n_iter`개만 랜덤 선택 → 시간 절약, 성능은 비슷하거나 가끔 더 좋음.
2. 총 fit 횟수 = `n_iter × cv` **+ 1 (refit)**.
3. `refit=False`면 최종 모델이 없어서 `predict`/`score` 불가.
4. `random_state`는 **RandomizedSearchCV에만** 있고, 조합 선택을 결정함 (GridSearchCV엔 없음).
5. 케라스 모델은 **함수(`build_model`) + 하이퍼파라미터 딕셔너리 + `KerasRegressor` 래퍼**로 사이킷런 랜덤 서치에 연결.
6. EarlyStopping / ReduceLROnPlateau를 쓰려면 **`validation_split`** 정의 필수.
7. **`n_jobs=-1` 남용 금지** → OOM 위험.
8. 은닉층은 사람도 컴퓨터도 "의미"를 알 수 없다 — 모델은 이해하는 게 아니라 **경사하강법으로 계산**할 뿐.
