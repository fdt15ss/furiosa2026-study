# TensorFlow / Keras 학습 정리

## 1. 스케일러(Scaler) 개요

데이터 전처리 단계에서 사용하는 스케일러들은 각각 특성이 다르며, 어떤 것이 가장 좋은지는 **데이터마다 다름** — 정답은 "다 써보고 성능 비교" 임.

- **MinMaxScaler**: 값을 0~1 사이로 변환. 최댓값으로 나누는 방식으로 동작.
- **StandardScaler**: 표준화(평균 0, 분산 1) 적용.
- **RobustScaler**: 이상치(outlier)에 가장 강함. 사분위값(IQR) 개념을 사용해 이상치의 영향을 줄여줌. 단, 이상치에 강하다고 해서 무조건 성능이 좋은 것은 아님.
- 4가지 스케일러 모두 실전에서 자주 사용되는 이유는 **데이터 구조만 보고 최적 스케일러를 판단하기 어렵기 때문** — 경험적으로 다 적용해보고 결과를 비교해 선택.

### 이상치 처리 관련 팁
- 스케일러가 이상치를 어느 정도 잡아주긴 하지만, 자동으로 이상치를 처리해주는 모델도 있음. 그래도 **사람이 직접 정제(휴먼 처리)하는 것이 AI에게 맡기는 것보다 낫다**는 게 일반적 견해.
- 데이터 정제는 가능한 한 **초기 단계(수집 직후)**에서 깔끔하게 해주는 것이 이후 단계에서 정제하는 것보다 성능에 유리.
- 스케일링은 보통 **모델에 데이터를 넣기 직전 단계**에서 수행.

## 2. 모델 저장 방식 비교

### 2-1. `model.save()` (SavedModel 방식)
- 모델 구조 + 가중치(weight) + 컴파일 정보까지 **전부 저장**.
- 저장 시점에 따라 결과가 다름:
  - **훈련 전에 저장** → 초기(랜덤) 가중치만 저장됨. 이후 `load_model()`로 불러오면 훈련 안 된 상태로 예측 → 성능 엉망.
  - **훈련(`fit`) 후에 저장** → 학습된 가중치까지 포함되어 저장됨.
- 저장 파일 용량이 `save_weights`보다 **더 큼** (모델 구조까지 포함하므로).

### 2-2. `model.save_weights()` 
- **가중치(weight) 값만** 저장, 모델 구조는 저장되지 않음.
- 불러올 때는 반드시 **동일한 모델 구조를 먼저 정의**한 후 `model.load_weights()`로 가중치만 불러와야 함.
- 모델 구조 없이 가중치만 불러오면 에러 발생.
- 컴파일 정보도 별도로 다시 해줘야 함 (compile 코드 필요).
- 파일 용량이 `save()`보다 작음 → 파라미터 수가 매우 많을 경우 용량 차이가 커짐.

### 2-3. 확장자 관련
- 과거에는 `.h5` 확장자를 주로 사용했으나, TensorFlow 버전이 올라가며 `.keras` 확장자를 권장하는 방식으로 변경됨.
- 버전에 따라 에러 메시지가 다를 수 있으므로, 에러가 나면 메시지를 확인 후 확장자 등을 수정.

### 정리: 언제 뭘 쓰나?
| 상황 | 추천 |
|---|---|
| 모델 구조까지 통째로 관리하고 싶을 때 | `save()` (SavedModel) |
| 가중치만 필요하고 모델 구조는 코드로 별도 관리할 때 | `save_weights()` |
| 일반적으로 편의성 우선 | `save()` (모델까지 저장, 용량 차이 크지 않다면) |

## 3. EarlyStopping

```python
from tensorflow.keras.callbacks import EarlyStopping

es = EarlyStopping(
    monitor='val_loss',
    mode='min',       # auto 도 가능
    patience=20,       # 개선 없어도 몇 epoch까지 참을지
    restore_best_weights=True,  # 가장 좋은 지점의 가중치로 복원
)
```
- `monitor`: 어떤 지표를 기준으로 조기 종료할지 (`val_loss`가 일반적. 검증 데이터 기준이라 더 명확한 지표로 간주됨)
- `patience`: 지정한 epoch 수만큼 개선이 없으면 훈련 종료
- 훈련 epoch 수(`epochs`)는 넉넉하게 주고, EarlyStopping이 알아서 중간에 끊도록 설계

## 4. ModelCheckpoint (핵심 콜백)

EarlyStopping과 함께 실무에서 가장 많이 쓰이는 콜백. **훈련 중 가장 성능이 좋은 지점(가중치)을 자동으로 저장**.

```python
from tensorflow.keras.callbacks import ModelCheckpoint

mcp = ModelCheckpoint(
    monitor='val_loss',
    mode='auto',
    save_best_only=True,
    verbose=1,
    filepath=file_path,  # 아래 4번 참고: 동적 파일명 생성
)

model.fit(x_train, y_train, callbacks=[es, mcp], ...)
```

- `save_best_only=True`: 매번 갱신될 때마다 최고 성능 지점만 덮어쓰기 저장 (동일 파일명 고정 시).
- `verbose=1`: 훈련 중 "val_loss improved" / "did not improve" 로그를 출력해 확인 가능.
- EarlyStopping과 함께 쓰면, EarlyStopping이 멈춘 시점이 아니라 **가장 성능이 좋았던 시점**의 가중치가 저장되어 있음 (`restore_best_weights=True` 옵션과 함께 쓰면 더 확실).
- 동일 이름으로 계속 덮어쓰면 **이력 관리가 안 됨** → 파일명에 날짜/시간/성능 수치를 넣어 매번 다른 이름으로 저장하는 방식을 권장 (아래 참고).

## 5. 동적 파일명 생성 (날짜 + 성능 지표 포함)

체크포인트 파일명에 생성 시각과 loss 값을 자동으로 넣어 이력 관리를 편하게 하는 방법.

```python
import datetime
import os

date = datetime.datetime.now()
date = date.strftime('%m%d_%H%M')  # 월일_시분 형태의 문자열

path = './_save/keras30/'
filename = '{epoch:04d}-{val_loss:.4f}.keras'

filepath = "".join([path, 'k30_', date, '_', filename])

mcp = ModelCheckpoint(
    monitor='val_loss',
    mode='auto',
    save_best_only=True,
    verbose=1,
    filepath=filepath,
)
```

- `datetime.datetime.now()`: 현재 시각 반환 (datetime 타입 객체)
- `strftime()`: datetime 객체를 원하는 형식의 **문자열**로 변환 (대소문자 구분 주의: `%m`=월, `%d`=일, `%H`=시, `%M`=분)
- `filename`의 `{epoch:04d}`, `{val_loss:.4f}`는 Keras가 fit 실행 중 자동으로 해당 epoch/성능 값을 채워 넣어주는 포맷 문자열
  - `04d`: 4자리 정수 형태
  - `.4f`: 소수점 넷째 자리까지 실수 형태
- 결과 예시: `k30_0914_1316_0374-0.2808.keras` → 9월 14일 13시 16분에 생성, 374 epoch에서 val_loss 0.2808로 저장됐다는 의미
- 이렇게 저장하면 대회 제출(Dacon/Kaggle 등) 파일 관리에도 매우 유용함.

## 6. Dropout

과적합(overfitting) 방지를 위한 기법. 학습된 파라미터가 많고 복잡한 데이터일수록 과적합 위험이 커지는데, 이를 완화.

```python
model.add(Dense(64, activation='relu'))
model.add(Dropout(0.2))   # 해당 레이어 출력의 20%를 랜덤하게 비활성화

model.add(Dense(32, activation='relu'))
model.add(Dropout(0.3))

model.add(Dense(16, activation='relu'))
model.add(Dropout(0.5))

model.add(Dense(1))  # 출력 직전 레이어에는 보통 Dropout 미적용
```

### 핵심 개념
- 모든 노드가 완전 연결(Fully Connected / Dense)되어 있을 때, 연산량이 많아짐 → 훈련 시마다 **일부 노드를 랜덤하게 제외**시키고 훈련.
- 매 epoch마다 랜덤하게 다른 노드가 빠지므로, 결과적으로 **매번 조금씩 다른 모델을 앙상블하는 효과** → 과적합 완화.
- **비율만 지정**하면 되고, 어떤 노드를 뺄지는 랜덤하게 결정됨 (특정 노드를 고정으로 빼는 것이 아님).
- 보통 Dropout 비율은 **0.5를 넘기지 않는 것이 일반적** (너무 많이 빼면 훈련 자체가 안 됨).
- **훈련(`fit`) 시에만 적용**되고, 평가/예측(`evaluate`, `predict`) 시에는 Dropout이 적용되지 않고 **모든 가중치를 사용**함 (자주 헷갈리는 부분).
- Dropout 적용 후 반드시 **기존(미적용) 모델과 성능 비교**해서 실제로 향상되는지 확인해야 함 — 항상 좋아지는 것은 아님.

## 7. Sequential 모델 vs Functional(함수형) 모델

### Sequential (기존 방식)
```python
model = Sequential()
model.add(Dense(64, input_dim=10))
model.add(Dense(32))
model.add(Dense(1))
```

### Functional API (함수형)
```python
from tensorflow.keras.models import Model
from tensorflow.keras.layers import Input, Dense

input1 = Input(shape=(10,))
dense1 = Dense(64)(input1)
dense2 = Dense(32)(dense1)
output1 = Dense(1)(dense2)

model2 = Model(inputs=input1, outputs=output1)
model2.summary()
```

### 비교
- 두 방식 모두 **동일 구조라면 파라미터 수, 성능이 완전히 동일** — 표현 방식(문법)만 다름.
- Functional 방식은 `Input` ~ `Output`까지 시작점과 끝점을 명시적으로 정의.
- `summary()` 출력 시 상단에 `Functional` vs `Sequential` 로 모델 타입이 구분되어 표시됨.
- Sequential은 순차적 구조라 구조에 제한이 있음 — **여러 입력/출력을 갖거나 복잡한 분기(앙상블 모델 등)를 만들 때는 반드시 Functional 방식**을 사용해야 함.
- Sequential → Functional로 단순 변환한다고 해서 원칙적으로 성능이 좋아지거나 나빠지지 않음 (문법 변경일 뿐).

## 8. 기타 실습 팁
- 코드에서 에러가 나면 겁먹지 말고 에러 메시지를 꼼꼼히 읽는 것이 중요 — 에러 메시지 자체가 무엇이 문제인지 알려줌.
- "문제는 에러가 안 떴을 때"라는 말처럼, 에러 없이 조용히 잘못된 결과가 나오는 경우가 더 위험할 수 있음.
- 버전이 올라가면서 API 세부 옵션(예: 확장자, 파라미터명)이 바뀌는 경우가 있으므로 항상 최신 문서/에러 메시지 기준으로 확인.
