## 2. LLM 서빙: Continuous Batching vs Overlap Scheduling

### 2-1. 개념 정리
| 구분 | 설명 |
|---|---|
| **Continuous Batching** | NPU에 여러 요청(여러 사용자)이 동시에 들어와도 연속적으로 배치를 구성해 처리. 현재 **기본(default) 방식** |
| **Overlap Scheduling** | NPU가 연산하는 동안 **놀고 있는 CPU가 다음 스케줄링을 미리 처리**해 유휴 시간을 없애는 방식. NPU 연산 ↔ CPU 스케줄링을 겹침(overlap) |

- 수업 비유: 4명이 키 1개를 공유하면 동시 접속은 되지만 느려지거나 튕김 → 이럴 때 배칭이 필요
- 병렬 처리 비교용으로 `ThreadPoolExecutor`(워커 1, 2, 4, 8)로 요청을 동시에 날려 측정

### 2-2. 서버 실행 옵션
```bash
# 기본 모드 (default)
<서버 실행 명령어>

# Overlap Scheduling 켜기
<서버 실행 명령어> --enable-overlap-schedule     # (옵션명 확인 필요)
```
- 서버 로그에 *scheduler started / overlap scheduler* 문구가 나오는지로 모드 확인

### 2-3. 벤치마크 지표 (F29/F30 실행 결과)
| 지표 | 의미 | 좋은 방향 |
|---|---|---|
| 총 요청 수 | 예: 8개 | - |
| 총 출력 토큰 | 예: 800개 (요청 8 × 토큰 100) | - |
| **총 소요 시간** | 전체 걸린 시간 | **작을수록 좋음** |
| **RPS** | Requests Per Second (초당 요청 처리량) | **클수록 좋음** |
| **TPS** | Tokens Per Second (초당 토큰 처리량) | **클수록 좋음** |

### 2-4. 실험 결과와 결론
- 토큰 수가 적은 소규모 테스트에서는 **차이가 거의 없거나 오히려 Overlap이 더 나쁘게** 나온 사람도 많음 (0.01초 단위 차이)
- 이전 서버 프로세스가 남아 있으면(Ctrl+Z) 결과가 틀어짐 → 재접속 후 재측정
- 토큰/프롬프트를 늘려 반복 측정(2~3회)하고, 워커 수(1/2/4/8)별로 비교
- **결론**: Overlap은 아직 기본값이 아닐 만큼 압도적이지 않음.
  - 배치 처리·여러 번 반복 실행 같은 상황에서만 선택적으로 사용
  - **"좋은 옵션이 있을 수 있으니 직접 테스트해 보고 고른다"**가 핵심
- 팁: 결과를 코드 하단에 주석으로 붙여두기 (`# 기본 모드`, `# overlap`)

## 3. Softmax 직접 구현 (keras78)

### 3-1. 개념
- 입력값들을 **0~1 확률로 바꾸고 합이 1**이 되게 만드는 함수
- 단순 비율(`x / sum(x)`)은 값의 차이가 작을 때 **변별력이 약함**
  - 예: [1,2,3,4] → 0.1, 0.2, 0.3, 0.4
- 그래서 **지수함수(eˣ)** 를 씌워 큰 값은 더 크게, 작은 값은 더 작게 만들어 차이를 극대화

### 3-2. 수식과 코드
$$\text{softmax}(x_i) = \frac{e^{x_i}}{\sum_j e^{x_j}}$$

```python
import numpy as np
import matplotlib.pyplot as plt

x = np.array([1, 2, 3, 4])

softmax = lambda x: np.exp(x) / np.sum(np.exp(x))

y = softmax(x)
print(y)          # 값이 큰 쪽(4)의 비중이 가장 커짐
print(np.sum(y))  # 1.0

ratio = y
labels = y
plt.pie(ratio, labels=labels, shadow=True, startangle=90)
plt.show()
```
- `e`(자연상수, 오일러 수)는 대략 **2.718…**. 계산할 때는 대충 2.7 정도로 생각
- 파이차트로 보면 가장 큰 값(4)의 조각이 압도적으로 큼
- 수업에서 일부러 `lambda`로 쓴 이유: **람다 함수 연습**

## 4. 경사하강법(Gradient Descent) 구현

### 4-1. 핵심 개념
- 학습 목표 = **Loss가 최소가 되는 최적의 가중치(weight)를 찾는 것**
- 미분 = **기울기**. 기울기가 0이 되는 지점 = 최저점
- Loss 함수(MSE)는 제곱 → **2차 함수** 모양 → 기울기를 따라 내려가면 최저점에 도달
- 용어: *Gradient Descent* = **경사하강법**

### 4-2. 예제 함수
$$f(x) = x^2 - 4x + 6 \quad\Rightarrow\quad f'(x) = 2x - 4$$
- 기울기가 0이 되는 지점: `x = 2` → `f(2) = 2` (최저점은 (2, 2))

```python
import numpy as np
import matplotlib.pyplot as plt

f = lambda x: x**2 - 4*x + 6
gradient = lambda x: 2*x - 4

x = -10.0          # 초기값
epochs = 50
learning_rate = 0.1

print("epoch\tx\tf(x)")
print(f"0\t{x:6.3f}\t{f(x):6.3f}")

for i in range(epochs):
    x = x - learning_rate * gradient(x)      # 경사하강법 갱신식
    print(f"{i+1}\t{x:6.3f}\t{f(x):6.3f}")
```
- `x`가 -10에서 시작해 **2로 수렴**하는 과정을 출력으로 확인
- 수렴이 안 되면 → ① epochs 늘리기 ② 너무 작게 갱신되면 learning rate 키우기

### 4-3. Learning Rate 실험 결과
| 설정 | 결과 |
|---|---|
| 0.1 정도 | 안정적으로 2로 수렴 |
| 너무 작음 | 수렴이 느려서 epoch 부족 |
| **1 이상** | 값이 튀며 **발산** (점점 멀어짐) |
- **learning rate는 하이퍼 파라미터 튜닝에서 가장 중요한 값 중 하나**
- 하이퍼 파라미터 튜닝 시 "일단 learning rate부터 조정"

### 4-4. 역전파와의 연결
$$w_{new} = w - \eta \cdot \frac{\partial \text{Loss}}{\partial w}$$
- `η` = learning rate, 기울기 = **Loss를 weight로 미분한 값**
- 위 코드의 `x`가 실제 학습에서는 **weight**에 해당
- 가중치(weight)와 기울기(gradient)는 **엄밀히는 다른 개념** (PyTorch 때 다시 설명 예정)
- 실무에서 레이어마다 Activation 하이퍼 파라미터를 하나하나 튜닝하는 것은 사실상 불가능 → 보통 **전체 설정 단위로 비교하고 성능 좋은 버전을 채택**
- 참고: "미분"이라는 용어가 일본어 번역에서 온 말이라 의미가 안 와닿지만, 그냥 **기울기**로 이해하면 쉬움

## 5. 가중치 갱신 실습 (keras79_learning_rate)

### 5-1. 설정
- `x = 10`, `y = 10`, 초기 `weight`(≠0, 예: 0.001), `learning_rate`, `epochs`는 **직접 조절**
- 모델: `hypothesis = x * w` (bias 없음, 합산(Σ) 없음 → 입력이 1개이므로)
- Loss:
  $$\text{loss} = (\text{hypothesis} - y)^2$$

### 5-2. 실습 포인트
```python
x, y = 10, 10
w = 0.001            # 초기 가중치
lr = ...             # 조절 대상
epochs = ...         # 조절 대상

for i in range(epochs):
    hypothesis = x * w
    loss = (hypothesis - y) ** 2

    up   = (x * (w + lr) - y) ** 2     # w를 올렸을 때 loss
    down = (x * (w - lr) - y) ** 2     # w를 내렸을 때 loss

    if up >= down:
        w = w - lr
    else:
        w = w + lr

    print(f"epoch: {i}  loss: {loss}  predict: {hypothesis}")
```
- 위 코드는 수업에서 설명한 **"loss가 작아지는 방향으로 w를 이동"** 개념을 정리한 것 (원본 코드와 세부 표현은 다를 수 있음 → 확인 필요)
- 목표: **마지막 predict가 10에 가깝게** (loss → 0)
- 조절해 보는 것: `epochs` 늘리기, `lr` 키우기/줄이기, 초기 `w`
- 한쪽은 loss가 줄고 반대쪽은 커지는 것을 확인 → 2차 함수의 기울기 방향 감각 익히기
- 수업 중 `lr`을 0.999 같은 큰 값으로 맞추라는 언급이 있었음 (녹취 불명확 → 확인 필요)
- 값이 수렴하는 과정 = **"수렴(convergence)"**

## 6. TensorBoard + CNN (keras80)

### 6-1. 개념
- **TensorBoard** = 학습 과정을 **시각화**해 주는 도구 (Loss/Accuracy 곡선, 모델 그래프, 히스토그램 등)
- PPT/보고서에 넣기 좋음 (직접 그린 그래프보다 깔끔)
- 면접에서 "TensorBoard도 써보셨어요?" 질문이 실제로 나옴 → **사용 경험을 꼭 만들어 둘 것**
  (선배 사례: 면접관이 그라디언트 디센트 써봤냐고 묻기도 함 — 기본 개념을 정확히 말할 수 있어야 함)

### 6-2. 환경
- 가상환경: `tf29x-gpu` (conda)
```bash
conda env list
conda activate tf29x-gpu
```
- Windows CMD 명령어: `cd`, `cls`(화면 정리), `dir` 등은 숙지

### 6-3. 모델 구성
- CNN: `Conv2D` 2개 → `Flatten` → `Dense` 층 (파라미터는 자유롭게)
- 컴파일: `categorical_crossentropy`, 옵티마이저 adam, metrics accuracy

### 6-4. 콜백 코드
```python
from tensorflow.keras.callbacks import EarlyStopping, TensorBoard

es = EarlyStopping(
    monitor='val_loss',
    mode='min',
    patience=50,
    verbose=1,
    restore_best_weights=True
)

# 로그 저장 경로 (파일 번호로 구분해서 저장 → 다른 실험과 안 겹치게)
tb = TensorBoard(
    log_dir='C:/study25/_save/tensorboard/keras80',
    histogram_freq=1,        # 히스토그램 주기
    write_graph=True,        # 그래프 저장
    write_images=True        # 이미지 저장
)

model.fit(x_train, y_train,
          epochs=..., batch_size=...,
          validation_split=0.2,
          callbacks=[es, tb])
```
- `ModelCheckpoint`는 저장하지 않을 거라 생략, `ReduceLROnPlateau`는 상황에 따라 사용
- 경로는 **절대경로** 사용 → 다른 실험과 겹치지 않도록 `keras80` 같은 **파일 번호 폴더**로 구분

### 6-5. TensorBoard 실행

  - 모르는 것은 **솔직하게 "모른다/신입이라 아직 모른다"** 라고 말하는 편이 신뢰도에 유리
- 취업 시장은 원래 항상 어려움. 포기하지 않고 **퀄리티를 올리는 것**이 답
- 연봉: 초봉은 낮을 수 있어도 **경력이 쌓이면 빠르게 상승**하는 구조

### 8-3. 학습 방법
- "코딩 자체"보다 **논문을 이해하고 설명·피칭하는 능력**이 연구소에서 더 중요
- **논문 읽기 팁**
  - 분야별 **핵심 논문(비전, LLM 등)** 을 완전히 흡수 → 질문에 답할 수 있을 정도까지
  - 핵심 논문 개수가 늘수록 이후 논문은 "여기만 보면 되겠다"가 보임
  - **IF(Impact Factor)가 높은 학회/저널** 논문 위주로 읽기
  - 배운 것은 **전부 정리**해 두기
- **발표 팁**: 발표 자료의 내용은 모든 질문에 답할 수 있는 수준까지 공부하고, **답할 수 없는 내용은 일부러 뺀다**
- 학부/비전공 출신은 **N수(반복 학습)** 로 쌓는 것이 정답
- 딥러닝 구조(데이터셋 → 모델 → 컴파일 → 훈련 4단계)를 몸에 익혀 두면 **어떤 논문이든 구현 가능** → "바이브 코딩이 아니라 논문 구현했다"가 강점

### 8-4. 실무 환경 (의료 AI)
- 병원 데이터는 **외부 API 사용이 어려움 → 폐쇄망(온프레미스) 개발이 기본**
- 개발용 서버급 PC를 병원에 설치해 포트로 연결하는 방식도 사용
- 데이터 사용 전 **IRB / DRB 승인** 필요
- **로컬 LLM(예: Gemma 계열)** 을 사용 — 한국어 의료 QA 정답률 기준으로 선정
- 의료 쪽은 파인튜닝보다 **도메인 지식·규칙을 RAG/에이전트로 입히는 것**이 핵심 (지식은 의료 종사자만 알고 있어서 **회의가 많고 개발은 짧게 끝남**)
- 프론티어 모델(Claude Code 등)은 **의료 데이터가 들어가지 않는 프로젝트**에만 사용, 폐쇄망에서 막힌 오류는 코드/에러 일부만 붙여 질문
- 음성(STT)은 Whisper 계열, 스택은 Python / PyTorch 중심 (요즘 TensorFlow는 잘 안 씀)
- **LLM 평가**: 의료진과 협의해 문제지를 제작
  - 간호 LLM 예: 문제 70%는 AI 생성, 약 30%는 간호대 교수가 보완
  - 중복·유사 문항은 **코드로 유사도 체크 후 사람이 검수**
  - 결과물이 논문 2편(문제지 논문 + 평가 논문)으로 나오기도 함

### 8-5. AI 도구 활용 방식 (바이브 코딩 시대)
- 퇴근 전 AI에 작업을 나눠 시켜 두고 다음 날 아침 확인하는 방식
- 에이전트를 **4개 정도로 역할 분리** (코드 작성 / 검증 / 사용자 컨펌 등) → 코드 품질 관리
- 프롬프트에 지침(rule)을 넣어 반복 절차를 고정
- 연구소는 AI 도입으로 **인력은 줄이고 장비(GPU)에는 투자**하는 추세

### 8-6. 대학원 팁
- AI 대학원 진학 시 **교수님께 미리 연락**하고 연구 계획을 보내는 것이 중요
- 일반 대학원은 이론/고전 중심 수업이 많아 **현업과 괴리**가 있다는 평가가 있어, 수업 자체보다 **연구실·교수님 선택**이 중요
- 특수대학원은 재학·논문 일정과 직장 병행 가능 (본인 체력 관리가 관건)
- 석사 필요성은 **분야·회사에 따라 다르며**, 의료 AI는 좋은 교수님 + 좋은 연구소 조합이면 충분히 가치 있음

### 8-7. 선배의 조언
- 발표 울렁증은 **횟수가 해결**한다 (세미나·발표 반복)
- 몸 상태가 나쁠 땐 **미리 강사에게 말하기** (미리 알리면 조정 가능)
- 기수 인맥·동기 네트워크가 큰 자산 → 평소 인성 관리
