## 1. 데이터 폴더 구조 & 라벨링

- `flow_from_directory` 방식을 사용하기 위해 폴더 구조를 아래처럼 맞춤:
  ```
  data/
    train/
      cat/   (예: 4000장)
      dog/   (예: 4006장)
    test/
      cat/   (예: 1000장)
      dog/   (예: 1013장)
  ```
- 폴더명(클래스명) 순서대로 라벨이 자동 부여됨 (예: `cat` → 0, `dog` → 1).
- macOS에서 압축을 풀면 생기는 `.DS_Store` 파일은 학습에 방해되므로 **반드시 삭제**.
  - Finder에서 "파일 확장명 보기" + "숨김 항목 보기" 체크해두면 관리 편함.
- 이미지 파일이 깨진 경우가 섞여 있을 수 있으므로 확인 필요.

## 2. 이미지 데이터 전처리 (Rescaling / Scaling)

- 이미지를 텐서(수치 데이터)로 변환하는 첫 단계는 **스케일링(정규화)**.
  - 픽셀값을 0~255 → 0~1 범위로 나눠주는 작업 (`rescale=1./255`).
- `ImageDataGenerator`를 사용하면:
  - 스케일링
  - 데이터 증강(회전, 뒤집기 등)
  - 배치 단위로 잘라서 제공
  을 한 번에 처리 가능.
- **중요:** 데이터 증강(회전/이동/뒤집기 등)은 **train 데이터에만 적용**하고, **test 데이터에는 적용하지 않음**.
  - test에 증강을 걸면 실제 정답 이미지가 왜곡되어 검증이 무의미해짐.

## 3. 이터레이터(Iterator) 데이터 형태

- `flow_from_directory`로 생성된 데이터는 **이터레이터(iterator)** 형태로 제공됨.
- 배치 단위로 묶여 있으며, 각 배치는 `(X, Y)` 튜플 형태:
  - `X`: 이미지 데이터, shape `(N, H, W, C)` (예: `(N, 150, 150, 1)`)
  - `Y`: 라벨 (원-핫 또는 0/1 형태)
- 전체를 한 번에 가져오고 싶으면 통배치(batch size = 전체 데이터 수)로 설정해서 한 번에 X, Y로 분리하는 방식도 가능.
  - 단, 데이터가 많으면 메모리 문제 발생 가능 → 배치 사이즈 조절 필요.

## 4. 모델 설계 — Dense Layer 파라미터 폭증 문제

- 문제 상황: Conv+Pooling 이후 Flatten을 거쳐 큰 Dense Layer(예: 512, 256 등)를 여러 개 쌓았더니
  - 파라미터 수가 수십만 개(예: 75만 개)까지 폭증.
  - 데이터 양이 적은데 파라미터가 너무 많아 **과적합(overfitting)** 및 성능 저하 발생.
- 원인 설명 (강사 비유):
  - Conv/Pooling까지는 이미지의 특징이 잘 압축되어 있는 상태.
  - 그런데 Dense Layer에서 필요 이상으로 크게 펼치면 압축된 특징 정보가 다시 "분산"되어 흐트러짐.
- **해결책**:
  1. Dense Layer의 유닛 수를 크게 줄임 (512 → 60~30 수준까지도 가능).
  2. Dense Layer 개수도 2~3개 정도로 축소.
  3. Conv Layer의 채널 수는 점진적으로 늘려가는 구조 권장 (예: 16 → 32 → 64 …, 작게 시작해서 점점 크게).
  4. **Flatten 대신 GlobalAveragePooling(GAP)** 사용을 권장.
     - GAP 이후에는 Dense를 크게 잡을 필요 없음 (이미 충분히 압축됨).
     - GAP → 작은 Dense 2~3개 → Sigmoid 출력 구조가 안정적.

## 5. 이진 분류 설정

- 출력층 활성화 함수: **Sigmoid**
- 손실 함수: **Binary Cross-Entropy**
- 평가지표: Accuracy

## 6. Target Size (이미지 크기) 트레이드오프

- 이미지 리사이즈 크기(target_size)에 따른 트레이드오프:
  - **작게 설정** (예: 150×150 이하): 학습 속도는 빠르지만 성능(정확도) 저하 가능.
  - **크게 설정** (예: 400×400 이상): 특징을 더 잘 살릴 수 있지만 학습 속도 느려지고 메모리 초과(OOM) 위험 증가.
  - 실습에서 시도한 값들: 150×150(안정), 200×200(안정권), 300×300(가능), 400×400(메모리 터짐).
- 결론: 데이터/장비 상황에 맞게 절충점을 찾아야 함 — 무조건 크다고 좋은 것도, 작다고 좋은 것도 아님.

## 7. 배치 사이즈(Batch Size) 관련

- 데이터 전체 장수(예: 4000장 이상)가 많을 경우 통배치로 처리 시 메모리 문제 발생 가능.
- 배치 사이즈를 줄이면 메모리 문제는 완화되지만, 너무 작으면 학습이 불안정해질 수 있음.
- 실습에서는 배치 사이즈를 16 → 120~160 수준으로 조정하며 테스트.
- **GPU 연산은 주로 학습(훈련) 단계에서 집중적으로 사용됨.**
  - `ImageDataGenerator` 자체의 데이터 처리는 CPU 연산 위주라 GPU 사용량이 적을 수 있음.

## 8. Early Stopping

- 콜백으로 Early Stopping 적용 (예: patience 값 20 설정 사례 언급).
- 검증 성능이 더 이상 개선되지 않으면 학습을 조기 종료하여 과적합 방지 및 시간 절약.

## 9. 실습 결과 참고 수치

- 여러 차례 모델 구조를 수정하며 정확도 개선 시도:
  - 초기: 0.5대 정확도(사실상 랜덤 수준) → Dense Layer 파라미터 과다가 원인으로 지목됨.
  - Dense Layer 축소 + GAP 적용 후: 0.7~0.8대까지 개선.
  - 최종적으로 목표치로 언급된 수치: **0.975 이상**.
